How to Debug a Typescript Program Running on K8s Using Dap in Emacs?

how to debug a typescript program running on k8s, using ms-vscode.js-debug and dap-mode?

TL;DR — recipe

  1. tsconfig.json has "inlineSourceMap": true (NOT just "sourceMap": true). External .js.map files require the adapter to read them from your local filesystem at the remote path, which forces you into localRoot=/=remoteRoot and the stale-dist/ class of bugs. Inline maps are extracted from the script content fetched over the inspector wire — no filesystem dependency. See why inline.

  2. Inspector reachable on localhost:9229:

    curl -s http://127.0.0.1:9229/json/version

    Empty/timeout means the port-forward isn’t up or the pod isn’t running node --inspect. Fix this first.

  3. Repo has .vscode/launch.json committed in the canonical shape (see canonical launch.json). dap-mode auto-discovers it via dap-launch-find-parse-launch-json; nothing to register in personal config.

  4. sourceMapPathOverrides keys MUST start with file:///. Plain /app/* does NOT match. Use file:///app/* → local path.

  5. M-x dap-breakpoint-add in a buffer, then M-x dap-debug → pick the launch.json entry. Fringe should turn solid; session pauses on hit.

  6. If the fringe stays hollow: M-x konix-dap-js/toggle-trace, redo, then check /tmp/vscode-js-debug.log — see diagnose hollow BP.

canonical launch.json

Lives at <repo>/.vscode/launch.json. Read automatically by dap-mode and by VS Code when the workspace is opened at the repo root.

{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "pwa-node",
      "request": "attach",
      "name": "Attach to <service>",
      "address": "localhost",
      "port": 9229,
      "cwd": "${workspaceFolder}/<package-dir>",
      "sourceMaps": true,
      "sourceMapPathOverrides": {
        "file:///<remote-prefix>/*": "${workspaceFolder}/<package-dir>/*"
      }
    }
  ]
}

Substitute:

  • <package-dir> = workspace package containing the running code. ${workspaceFolder} expands to lsp-workspace-root.
  • <remote-prefix> = absolute path inside the pod where the code runs (typically the container WORKDIR, e.g. /app).

Do not set localRoot=/=remoteRoot. Those make vscode-js-debug load the running .js and any external .js.map from the local filesystem at the mapped path; if a stale local dist/ exists, the adapter reads it and silently misses any module added since. sourceMapPathOverrides alone makes vscode-js-debug fetch script content from V8 over the wire, always in sync with the running process.

Use pwa-node, not node. dap-mode reserves node for the legacy ms-vscode.node-debug2; vscode-js-debug binds to pwa-node.

pitfalls

sourceMapPathOverrides key without file:/// scheme

The matcher applies patterns against the resolved file:// URL. /app/* never matches; file:///app/* does. (../../../../* also matches against the raw sources entry of TS-emitted maps, but it’s depth-dependent and not portable across files.)

resolveSourceMapLocations filters too aggressively

Globs are interpreted relative to the workspace folder, but the running script URLs are file:///app/dist/... (outside any workspace). Even ["**", "!**/node_modules/**"] filters them all out and source maps never register. Leave it unset (default null = unrestricted).

stale local dist/

If a stale build of dist/ exists locally and localRoot=/=remoteRoot is set, the adapter reads the stale file and silently fails to bind BPs on any newer code. Either delete local dist/ or stick to sourceMapPathOverrides (recommended).

--watch drops the inspector on every save

nest start --debug --watch and similar restart node on every source change → the inspector port closes and reopens → the attached dap session dies. Reattach (M-x dap-debug) after each save.

breakpoints are bound asynchronously

The first setBreakpoints response often comes back with empty breakpoints: [] — that’s normal. The adapter sends a later breakpoint event with verified: true once the matching script loads. If that event never arrives, the BP didn’t bind.

the request URL must reach the handler

A 400 from a guard or pipe (e.g., ParseUUIDPipe rejecting a non-UUID path param) means the handler body never runs regardless of the debug config. Always curl -i first to check the status code.

diagnose a hollow BP

When the BP marker stays hollow / V8 doesn’t pause:

  1. M-x konix-dap-js/toggle-trace to enable the verbose CDP log.
  2. M-x dap-debug → reattach.
  3. Trigger the code path.
  4. Read /tmp/vscode-js-debug.log (overwritten on each new session).

Most useful: runtime.sourcecreate for your file:

grep 'Creating source from source map' /tmp/vscode-js-debug.log \
  | grep <your-file>.controller \
  | head -1 \
  | python3 -c 'import sys,json; [print(json.dumps(json.loads(l)["metadata"], indent=2)) for l in sys.stdin]'

Read metadata.absolutePath:

  • Remote path (e.g. /app/src/...): override didn’t match. Most often, key is missing the file:/// scheme.
  • Local path that doesn’t exist (often with stray ../): replacement value is wrong; the captured * is being substituted where it shouldn’t.
  • Correct local path: the override works; the issue is elsewhere. Inspect setBreakpoints in the same log: 
    grep '"command":"setBreakpoints"' /tmp/vscode-js-debug.log
    The response should have breakpoints[].verified: true (possibly via a later breakpoint event). If it stays [] or verified: false, the adapter found no script the source maps to — usually a script-load timing issue or a resolveSourceMapLocations filter.

Also useful, in *Messages* (with dap-print-io on):

  • setBreakpoints request body: confirm source.path is what you expect.
  • breakpoint events: reason: "changed" with verified: true = bound.

prerequisites in personal Emacs config

In KONIX_AL-dap-js.el (or equivalent):

(setq dap-js-debug-program '("dap-js-debug-server.sh"))
(setq dap-print-io t  dap-inhibit-io nil)
(setq message-log-max 200000)  ; otherwise DAP traffic rolls out fast

;; Trace toggle - keeps :trace out of the committed launch.json.
(defconst konix-dap-js/trace-log-file "/tmp/vscode-js-debug.log")
(defun konix-dap-js/inject-trace (orig conf &rest args)
  (let ((conf (if (and (string= (plist-get conf :type) "pwa-node")
                       (not (plist-member conf :trace)))
                  (append conf
                          (list :trace (list :console t :stdio t
                                             :logFile konix-dap-js/trace-log-file)))
                conf)))
    (apply orig conf args)))
(defun konix-dap-js/toggle-trace (&optional arg)
  (interactive "P")
  (let* ((on (advice-member-p 'konix-dap-js/inject-trace 'dap-debug))
         (turn-on (cond ((null arg) (not on))
                        ((<= (prefix-numeric-value arg) 0) nil)
                        (t t))))
    (if turn-on
        (progn (advice-add 'dap-debug :around #'konix-dap-js/inject-trace)
               (message "dap-js trace ON -> %s" konix-dap-js/trace-log-file))
      (advice-remove 'dap-debug #'konix-dap-js/inject-trace)
      (message "dap-js trace OFF"))))
  • Do NOT register a project-specific dap-register-debug-template. launch.json is the source of truth.
  • The trace advice is OFF by default; toggle on only when investigating.
  • message-log-max must be set BEFORE the session if you want to read DAP traffic from *Messages* afterwards (default 1000 lines rolls fast).

trace toggle

M-x konix-dap-js/toggle-trace flips the advice that injects :trace into any pwa-node config that doesn’t already specify one.

  • No prefix: toggle.
  • C-u 1 M-x …: force ON.
  • C-u 0 M-x …: force OFF.

When ON, every fresh session writes a CDP log to /tmp/vscode-js-debug.log containing every Debugger.scriptParsed, source-map fetch, setBreakpointByUrl attempt, and breakpointResolved event. The file is overwritten on each new session — read it (or copy it) before reattaching.

port forwarding

Create a port forward on 9229 to communicate with the remote node over the inspector protocol. With Tilt: k8s_resource("<deployment>", port_forwards[“9229:9229”])= in the Tiltfile. Otherwise: kubectl port-forward deploy/<deployment> 9229:9229.

Error: Could not connect to debug target at http://localhost:9229: Could not find any debuggable target means the connection is broken. Confirm the inspector is reachable:

curl -s http://127.0.0.1:9229/json/version

Healthy response: { "Browser": "node.js/v...", "Protocol-Version": "1.1" }.

Restarting the pod is sometimes the fastest fix; refreshing code while a debugger is attached can wedge the inspector. nestjs --watch is particularly prone to Starting inspector on 127.0.0.1:9229 failed: address already in use after rapid reloads.

clean slate

When dap-mode and vscode-js-debug processes wedge across reloads:

(when (dap--session-running (dap--cur-session))
  (dap-disconnect (dap--cur-session-or-die)))
(konix/dap-delete-all-sessions)

And, last resort, from the shell:

pkill -f js-debug
pkill -f ms-vscode

why inline source maps

vscode-js-debug fetches a script’s source map in one of three ways:

  1. Inline: the .js contains a //# sourceMappingURL=data:application/json;base64,… line. The adapter extracts the map directly from the script content it gets via Debugger.getScriptSource over the inspector wire. No filesystem access is needed.
  2. External .js.map: the .js contains a relative URL like //# sourceMappingURL=foo.js.map. The adapter resolves it against the .js’s file:// URL and reads the .js.map from disk. There is no CDP method to fetch a sidecar map over the wire — V8 only ships the script content.
  3. HTTP-served map: the URL in the sourceMappingURL comment is http(s)://... and the adapter fetches it via HTTP. Doesn’t apply to the typical k8s/Tilt setup.

For a remote pod, option 2 means the adapter looks for /<remote-prefix>/dist/.../X.js.map on your local filesystem. That forces localRoot=/=remoteRoot mapping back into the picture, with every problem that brings (stale dist/, hoisted node_modules layout, divergence after deploy). Inline maps remove the entire category by carrying the mapping inside the script V8 already has.

Set "inlineSourceMap": true in tsconfig.json (mutually exclusive with "sourceMap": true). Optionally "inlineSources": true embeds the original .ts content too — useful if the local checkout might not match the running build (e.g., stepping through code committed before you switched branches).

{
  "compilerOptions": {
    "target": "ES2024",
    "module": "nodenext",
    "outDir": "./dist",

    "inlineSourceMap": true,
    // "inlineSources": true,  // optional: embed the .ts content too

    // Make sure these are NOT set, or set to false:
    // "sourceMap": false,
    // "removeComments": false  // (irrelevant to debug, but keeps the
    //                              embedded `// # sourceMappingURL=...`
    //                              line readable in the .js)
  }
}

Verify on a built file:

# Should print a single line ending in a base64 "data:" URL
tail -c 200 dist/path/to/file.js | grep -o 'sourceMappingURL=[^ ]*'

Healthy output looks like sourceMappingURL=data:application/json;base64,eyJ2ZXJzaW9uIjoz…. If it instead points to a relative .js.map file (e.g., sourceMappingURL=file.js.map) you have the external-map shape and the recipe in this doc won’t work without localRoot=/=remoteRoot.

worked example: NestJS in /app

Typical setup the recipe matches:

  • Pod runs pnpm run start:debug (= nest start --debug --watch). Nest compiles TS to /app/dist/ and runs node /app/dist/src/main.js with --inspect on.
  • tsconfig.json sets "inlineSourceMap": true — no external .js.map files exist; the base64 sourceMappingURL is embedded in each .js.
  • The container WORKDIR is /app. The repo is checked out locally at ${workspaceFolder}, with the Nest package under ${workspaceFolder}/backend/nestjs.

Concrete .vscode/launch.json for that setup:

{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "pwa-node",
      "request": "attach",
      "name": "Attach to backend",
      "address": "localhost",
      "port": 9229,
      "cwd": "${workspaceFolder}/backend/nestjs",
      "sourceMaps": true,
      "sourceMapPathOverrides": {
        "file:///app/*": "${workspaceFolder}/backend/nestjs/*"
      }
    }
  ]
}

Source map “sources” entry resolution chain for a controller at backend/nestjs/src/foo/bar.controller.ts:

raw entry:        ../../../../src/foo/bar.controller.ts
resolved against: file:///app/dist/src/foo/bar.controller.js
resolves to:      file:///app/src/foo/bar.controller.ts
override applies: file:///app/* -> ${workspaceFolder}/backend/nestjs/*
final local path: <repo>/backend/nestjs/src/foo/bar.controller.ts

The number of ../ in the raw entry depends on the depth of the file inside src/, which is why a depth-anchored override key (../../../../*) is brittle while a scheme-anchored one (file:///app/*) is not.

historical: trace log shape

Useful events in the trace log (format unchanged since 2024):

Debugger.scriptParsed   - V8 told the adapter a script loaded.
                          Confirms the .js you care about is visible.
sourcemap.parsing       - adapter parsing a source map (inline or otherwise).
runtime.sourcecreate    - adapter registering a source. Look at
                          metadata.absolutePath - that's THE path
                          dap-mode's setBreakpoints will be matched against.
loadedSource event      - adapter telling dap-mode about a source.
breakpoint event        - verified true/false; the BP-binding answer.
stopped event           - V8 paused.

beware the location of node_modules — only with localRoot=/=remoteRoot

When using localRoot=/=remoteRoot (no longer recommended), the local path of dependencies must mirror the remote layout. In a yarn/pnpm workspace, deps may be hoisted to a different root locally than they are in the container, so node_modules/dep/foo.js won’t resolve. With sourceMapPathOverrides alone (over-the-wire script fetch) this category of bug disappears.
