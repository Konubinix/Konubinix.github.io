Décompiler France Identité Pour Lire L'attestation

Fleeting

tl;dr: France Identité n’utilise pas Play Integrity ; elle s’appuie sur l’attestation matérielle de clé (SDK Idakto iddvk). Or cette attestation transmet au serveur, par construction, l’identité de l’app — nom de paquet et empreinte du certificat signataire. Un client libre re-signé s’attesterait donc comme une app différente, que le serveur peut distinguer et rejeter. Le point de décision penche vers client verrouillé ; reste l’inconnue serveur (le backend épingle-t-il cet identifiant ?), non vérifiable côté client.

But : trancher le point de décision laissé ouvert par france identité en foss ? — un client tiers libre pourrait-il passer, ou le serveur vérifie-t-il aussi l’identité de l’app (signature) ? La méthode est celle de removing ads from the gallery app : décompiler l’APK officiel. Ici elle ne sert pas à patcher mais à lire le code : voir quel mécanisme d’attestation l’app emploie, et si ce mécanisme transmet la signature de l’app.

Chaque étape ci-dessous est un bloc exécutable ; la note se rejoue de bout en bout.

télécharger le XAPK

France Identité est distribué en .xapk (un zip contenant l’APK de base et les split APK). L’endpoint version=latest d’APKPure redirige vers une URL signée fraîche à chaque appel — le bloc reste rejouable.

rm -rf fi-disassembled fr.gouv.franceidentite.apk config.arm64_v8a.apk manifest.json
curl -sL -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64)" \
  -o fi.xapk "https://d.apkpure.com/b/APK/fr.gouv.franceidentite?version=latest"
ls -lh fi.xapk

-rw-r--r-- 1 sam users 69M Jul 18 09:41 fi.xapk

extraire l’APK de base

L’APK de base porte le classes.dex et le manifeste ; c’est lui qu’on décompile. On récupère aussi manifest.json pour lire la version obtenue.

unzip -o fi.xapk fr.gouv.franceidentite.apk config.arm64_v8a.apk manifest.json
echo "--- version obtenue ---"
grep -o '"version_name":[^,]*' manifest.json

chercher Play Integrity (attestation d’app par Google)

L’API Play Integrity de Google renvoie un verdict qui inclut le champ appIntegrity (empreinte des certificats de l’app). Si l’app l’utilise, elle transmet son identité à Google, et le serveur peut refuser tout client tiers. On cherche ses classes (com.google.android.play.core.integrity) dans le smali.

echo "=== références Play Integrity / SafetyNet ==="
grep -rl -e "play/core/integrity" -e "PlayIntegrity" -e "IntegrityManager" \
        -e "safetynet" -e "SafetyNet" fi-disassembled/smali* 2>/dev/null | head -30
echo "=== occurrences ==="
grep -rc -e "play/core/integrity" -e "IntegrityManager" -e "SafetyNet" \
        fi-disassembled/smali* 2>/dev/null | grep -v ':0$' | head -30

chercher l’attestation matérielle de clé (Android Keystore)

L’attestation matérielle de clé certifie l’appareil (amorçage vérifié) sans Google. On isole l’appel qui la déclenche — setAttestationChallenge — et l’export de la chaîne de certificats — getCertificateChain — envoyée au serveur.

echo "=== setAttestationChallenge ==="
grep -rl "setAttestationChallenge" fi-disassembled/smali* 2>/dev/null
echo "=== getCertificateChain (fr.gouv / idakto uniquement) ==="
grep -rl "getCertificateChain" fi-disassembled/smali* 2>/dev/null \
  | grep -e "idakto" -e "franceidentite"

lire la méthode d’attestation dans le SDK Idakto

com.idakto.iddvk est le SDK de sécurité (éditeur Idakto). On lit le corps de la méthode : clé EC secp256r1, défi setAttestationChallenge reçu en paramètre ([B, donc fourni de l’extérieur — le serveur), puis test de android.hardware.strongbox_keystore (élément sécurisé préféré). C’est le flux canonique d’attestation matérielle pilotée par le serveur.

f=fi-disassembled/smali/com/idakto/iddvk/iDDvk.smali
grep -n -e "secp256r1" -e "setAttestationChallenge" -e "strongbox_keystore" \
        -e "getCertificateChain" "$f"

chercher la signature de l’app et sa transmission

Le c\oeur du point de décision : l’app lit-elle sa propre signature (getPackageInfo ... GET_SIGNATURES, signingInfo) pour la transmettre ? On cherche les API de lecture de signature et les chaînes d’intégrité/racine.

echo "=== lecture de la signature de l'app ==="
grep -rl -e "GET_SIGNATURES" -e "GET_SIGNING_CERTIFICATES" \
        -e "signingInfo" -e "getSignatures" fi-disassembled/smali* 2>/dev/null | head -30
echo "=== root / intégrité / trafiqué ==="
grep -rl -e "RootBeer" -e "rootbeer" -e "isRooted" -e "Magisk" \
        fi-disassembled/smali* 2>/dev/null | head -30

ce que la décompilation établit

Trois faits, tous rejouables ci-dessus :

  • Pas de Play Integrity. Aucune référence à play/core/integrity, IntegrityManager ni SafetyNet dans le bytecode. L’app ne délègue pas l’attestation à Google — cohérent avec son fonctionnement sur /e/OS.
  • Attestation matérielle de clé, pilotée par le serveur. Le SDK Idakto com.idakto.iddvk génère une clé EC secp256r1 dans l’Android Keystore avec un défi reçu en paramètre (setAttestationChallenge([B) — donc un nonce extérieur, le serveur), préfère l’élément sécurisé (android.hardware.strongbox_keystore), puis exporte la chaîne de certificats (getCertificateChain) vers le serveur. C’est le flux canonique d’attestation matérielle.
  • Pas d’auto-lecture de signature, pas de détecteur de root. Aucun GET_SIGNATURES, signingInfo, ni bibliothèque type RootBeer/Magisk : l’assurance d’intégrité n’est pas faite au niveau applicatif, elle est déléguée à l’attestation matérielle (et au natif Idakto).

Le point de décision se tranche alors sans supposer le code serveur. La chaîne de certificats d’attestation d’Android porte une extension attestationApplicationId — « the Android platform’s belief as to which apps are allowed to use the secret key material under attestation »1, soit le nom de paquet et l’empreinte du certificat signataire, renseignés par la plateforme, non par l’app. Le serveur reçoit donc, lié cryptographiquement au défi, quelle app a produit l’attestation.

Conséquence : une réimplémentation native libre, signée d’une autre clé sous un autre paquet, présenterait un attestationApplicationId différent — que le serveur peut trivialement distinguer et refuser. La faisabilité d’un client tiers libre ne dépend donc plus que d’une politique serveur invisible depuis le client : le backend épingle-t-il cet identifiant d’app ? Le mécanisme pour le faire est présent par construction ; pour une app d’identité régalienne, parier qu’il ne l’utilise pas serait imprudent.
