Fleeting

Each device that wants to participate in the sync needs an authz token — the traefik authz-check-path middleware (cf. the nomad job) gates the WebSocket endpoint behind a one-shot magic-link. clk authorizationserver generate mints such a link, with the ?sync_url…= already baked in so the receiving device arms its localStorage on first open. The path tinybasesync/organiser scopes a TinyBase room (cf. WsServer addPathIdsListener) — distinct apps reuse the same container without crossing streams.

choice of technology

Two prior attempts ground the choice.

The first was score counter tally, built on alpine + yjs. The friction came from two reactivity systems competing: alpine drives the DOM from its own reactive store, yjs drives everything from its document, and the wiring between the two is where the bugs lived.

The second was scrutin de Condorcet randomisé entre amis, on petite-vue

  • automerge. Slightly better — petite-vue is more forgiving than

alpine — but the same fault line was there: the framework’s reactivity and the CRDT’s reactivity are not the same animal, and keeping them in step needed hacky magick at every seam.

The lesson points one way. The next combo must have a single source of reactivity: the data store and the rendering layer should be the same animal, with the UI subscribing to the store directly rather than to a framework state that happens to mirror it. On top of that, this is a line-of-business app — lists, forms, CRUD over labelled boxes — and the friction floor of React (components, hooks, effect dependencies, build pipeline) buys nothing at this scale.

The pick: TinyBase. A reactive store with persistence and mergeable sync built in. The DOM subscribes to store events directly — one reactivity system by construction. No framework, no JSX, no build pipeline.

Open the app

With no box recorded yet, the screen has nothing to show. An empty- state — emoji, title, a one-line hint — names the state honestly so the user knows the app starts empty and not stuck loading.

Add a box

An empty app needs a way out of the empty state. A box is recorded by its photo — taken with the phone’s camera or picked from the gallery. The photo is the only thing the user sees of a box from then on; nothing else is needed to identify it.

  • Entry point. An always-visible Add a box button in the top bar; the user can record another one without re-traversing the empty-state hint.
  • Save plumbing. crypto.randomUUID() for the id, store.setRow for the write, the tables listener re-runs render.
  • Form toggle. openForm(selector) shows the named form and hides any other — a no-op for now, but the next chapter adds a second form and the toggle keeps them mutually exclusive.
  • Photo pipeline. fileToThumbnail, pendingBoxPhoto, the change handler on the file input — same machinery as items, see Items with photos for the full description.

The same form serves add and edit (cf. Edit a box). editingBoxId, empty by default, tracks which row Save should overwrite — empty means insert a fresh UUID. The Add a box button always resets to add-mode; the edit chapter is what flips it the other way.

Helpers first: openForm toggles between forms, the box-form state vars track edit mode and the pending photo, resetBoxPhotoPreview swaps the preview img source, and the file-input change listener funnels uploads through the shared fileToThumbnail (cf. Items with photos) into pendingBoxPhoto.

function openForm(which){
    const forms = ['[data-add-form]', '[data-add-item-form]'];
    for(const sel of forms){
        document.querySelector(sel).hidden = (sel !== which);
    }
}

let editingBoxId = '';
let pendingBoxPhoto = '';
let pendingBoxPhotoName = '';

function resetBoxPhotoPreview(src){
    const preview = document.querySelector('[data-box-photo-preview]');
    if(src){
        preview.src = src;
        preview.hidden = false;
    } else {
        preview.hidden = true;
        preview.removeAttribute('src');
    }
}

document.querySelector('#addBoxPhoto').addEventListener('change', async e => {
    const file = e.target.files[0];
    if(!file){
        pendingBoxPhoto = '';
        pendingBoxPhotoName = '';
        resetBoxPhotoPreview('');
        return;
    }
    pendingBoxPhoto = await fileToThumbnail(file);
    pendingBoxPhotoName = file.name.replace(/\.[^.]+$/, '');
    resetBoxPhotoPreview(pendingBoxPhoto);
});

Actions next: open the form (clearing prior state), cancel (discards the pending photo), or submit (writes the row with a fresh order index appended at the end of the list).

    pendingBoxPhoto = '';
    pendingBoxPhotoName = '';
    document.querySelector('#addBoxPhoto').value = '';
    resetBoxPhotoPreview('');
    document.querySelector('[data-delete-box]').hidden = true;
    openForm('[data-add-form]');
});

document.querySelector('[data-cancel-add]').addEventListener('click', () => {
    editingBoxId = '';
    document.querySelector('[data-add-form]').hidden = true;
});

document.querySelector('[data-add-form]').addEventListener('submit', e => {
    e.preventDefault();
    if(!pendingBoxPhoto) return;
    const id = editingBoxId || crypto.randomUUID();
    const existing = store.getRow('boxes', id);
    const orders = Object.values(store.getTable('boxes')).map(r => r.order ?? 0);
    const order = existing?.order ?? (orders.length ? Math.max(...orders) + 1 : 0);
    store.setRow('boxes', id, {
        photo: pendingBoxPhoto,
        photoName: pendingBoxPhotoName,
        order,
    });
    editingBoxId = '';
    pendingBoxPhoto = '';
    pendingBoxPhotoName = '';
    document.querySelector('[data-add-form]').hidden = true;
});

Listing the boxes is its own contribution to js-render-body. Each box renders as a photo thumbnail (the only thing the user sees of the box itself), followed by its items as chips, with the reorder grip at the right edge. The thumbnail is wrapped in a <button> whose aria-label carries Box <photoName> — that’s how a click-to-edit gesture reaches it (cf. Edit a box), how a screen reader names it, and how tests address it without baking a CSS class into a query.

Building one box card is a five-step assembly — the wrapping <li>, the photo button, the nested items list, the grip, and the final append. Extracted into renderBoxEl so the loop above stays readable.

function renderBoxEl(id, idx, row, itemsById, itemMatches){
    const li = document.createElement('li');
    li.className = 'box reorder-item';
    li.setAttribute('data-box-id', id);
    li.setAttribute('data-drop-target', '');
    li.setAttribute('data-idx', idx);

    const photoBtn = document.createElement('button');
    photoBtn.type = 'button';
    photoBtn.className = 'box-photo';
    photoBtn.setAttribute('aria-label', `Box ${row.photoName}`);
    const photoImg = document.createElement('img');
    photoImg.className = 'box-photo-thumb';
    photoImg.src = row.photo;
    photoImg.alt = '';
    photoBtn.append(photoImg);

    const itemsList = document.createElement('ul');
    itemsList.className = 'items-in-box';
    const containedIds = Object.keys(itemsById).filter(iid =>
        itemsById[iid].boxId === id && itemMatches(itemsById[iid].name));
    for(const iid of containedIds){
        itemsList.append(renderItemEl(iid, itemsById[iid]));
    }

    const grip = document.createElement('button');
    grip.type = 'button';
    grip.className = 'reorder-grip';
    grip.setAttribute('aria-label', `Reorder ${row.photoName}`);
    grip.innerHTML = '<svg width="10" height="16" viewBox="0 0 10 16" aria-hidden="true">'
        + '<circle cx="2" cy="3" r="1.3"/><circle cx="8" cy="3" r="1.3"/>'
        + '<circle cx="2" cy="8" r="1.3"/><circle cx="8" cy="8" r="1.3"/>'
        + '<circle cx="2" cy="13" r="1.3"/><circle cx="8" cy="13" r="1.3"/>'
        + '</svg>';

    li.append(photoBtn, itemsList, grip);
    return li;
}

The loop sorts boxes by order, filters by the active search (a box with no item matching the query is hidden), then replaces the list’s children with the rebuilt cards.

const list = document.querySelector('[data-boxes-list]');
const rows = store.getTable('boxes');
const itemsById = store.getTable('items');
const queryB = (document.querySelector('[data-search]')?.value || '').trim().toLowerCase();
const itemMatchesB = name => !queryB || name.toLowerCase().includes(queryB);
const sortedIds = Object.keys(rows).sort((a, b) =>
    (rows[a].order ?? 0) - (rows[b].order ?? 0));
const ids = sortedIds.filter(id => {
    if(!queryB) return true;
    return Object.keys(itemsById).some(iid =>
        itemsById[iid].boxId === id && itemMatchesB(itemsById[iid].name));
});
list.hidden = !ids.length;
list.replaceChildren(...ids.map((id, idx) =>
    renderBoxEl(id, idx, rows[id], itemsById, itemMatchesB)));

Edit a box

A wrong photo — the cheapest fix is to tap the box itself.

  • Click target. The photo button. Items inside the box ([data-draggable]) and the reorder grip (.reorder-grip) are early-returned by the handler — each has its own gesture.
  • Tap behaviour. Prefills the form (cf. Add a box) with the current photo and sets editingBoxId.
  • Save behaviour. Overwrites the row in place via TinyBase’s setRow — same key, listener fires once, the box re-renders.

Delete a box

Deleting a box must not destroy what’s filed inside it.

  • Items survive. Each item with the deleted boxId flips back to the empty string (Unassigned) before the box’s row is removed.
  • Order matters. Item boxId updates before store.delRow on boxes — otherwise listeners fire on already-orphaned references.
  • Accidental tap protection. confirm() sits in front, picked up by Playwright via page.once("dialog", ...) in the test.

@testcase
def test_delete_box(page):

Reorder boxes

Boxes pile up in creation order, but the user wants them by physical layout — which shelf, which drawer. A small grip on each box’s right edge hosts the gesture.

  • Engine. The shared reorder engine handles the drag; we feed it its conventions: .reorder-list on the <ul>, .reorder-item + data-idx on each <li>, .reorder-grip for the handle.
  • Event. On reorder:move, we splice the order cells in the store; the next render reflects the new sequence.
  • Why an explicit order. Table iteration order survives a reload but not an edit or a delete-and-recreate. An order integer per row keeps one source of truth, queried in render via a sort.
  • Why a transaction. Splicing rewrites every box’s order in one pass; store.transaction(...) collapses these into a single listener firing — otherwise the engine’s geometry queries would chase a moving target during the drag.
  • Why the grip aria-label. Reorder <photoName> lets a test pick the right handle without leaking a class name. The grip is also early-returned from the box-edit click handler (cf. Edit a box) so tapping it doesn’t open the edit form.

@testcase
def test_reorder_boxes(page):
    """Dragging a box's grip up changes its position in the list."""
    clear_state(page)
    for name in ["alpha", "bravo", "charlie"]:
        page.get_by_role("button", name="Add a box").click()
        page.get_by_label("Photo").set_input_files(files=[{
            "name": f"{name}.png",
            "mimeType": "image/png",
            "buffer": MINIMAL_PNG,
        }])
        page.get_by_role("img", name="Photo preview").wait_for(state="visible")
        page.get_by_role("button", name="Save").click()
    boxes = page.get_by_role("button", name=re.compile(r"^Box "))
    first_label = boxes.first.get_attribute("aria-label")
    assert first_label == "Box alpha", \
        f"unexpected initial first box: {first_label!r}"
    page.get_by_role("button", name="Reorder charlie").drag_to(
        page.get_by_role("button", name="Reorder alpha"))
    boxes = page.get_by_role("button", name=re.compile(r"^Box "))
    first_label = boxes.first.get_attribute("aria-label")
    assert first_label == "Box charlie", \
        f"reorder didn't take effect: first is {first_label!r}"
    print("  PASS: reorder boxes")


document.addEventListener('reorder:move', e => {
    if(e.target.dataset?.reorder !== 'boxes') return;
    const { from, to } = e.detail;
    const rows = store.getTable('boxes');
    const ordered = Object.keys(rows).sort((a, b) =>
        (rows[a].order ?? 0) - (rows[b].order ?? 0));
    const [moved] = ordered.splice(from, 1);
    ordered.splice(to, 0, moved);
    store.transaction(() => {
        ordered.forEach((id, idx) => store.setCell('boxes', id, 'order', idx));
    });
});

Add an item

Boxes alone are scaffolding. The point of the app is the items inside them — every screw, charger, allen key the user wants to retrieve later. Items enter the system without a box: a free-text name, then dragged into the right box once the user finds it (the drag-n-drop lands in the next chapter). The pile of unboxed items shows up in an Unassigned section so they don’t get lost.

An item is a row in a second TinyBase table, items, keyed by id, with a name, a boxId that defaults to the empty string, and an optional image (cf. Items with photos for the upload pipeline that fills it). The empty boxId is what the unassigned render filters on.

async function fileToThumbnail(file){
    const url = URL.createObjectURL(file);
    try {
        const img = await new Promise((res, rej) => {
            const i = new Image();
            i.onload = () => res(i);
            i.onerror = rej;
            i.src = url;
        });
        const max = 200;
        const scale = Math.min(max / img.width, max / img.height, 1);
        const canvas = document.createElement('canvas');
        canvas.width = Math.max(1, Math.round(img.width * scale));
        canvas.height = Math.max(1, Math.round(img.height * scale));
        canvas.getContext('2d').drawImage(img, 0, 0, canvas.width, canvas.height);
        return canvas.toDataURL('image/jpeg', 0.85);
    } finally {
        URL.revokeObjectURL(url);
    }
}

Items with photos

A name like “3mm screw” is a poor search target when you’re standing in the workshop holding the actual thing. A photo — even a tiny one — closes the gap between the inventory and the physical object. The same pipeline drives box photos (cf. Add a box).

  • Capture. File input with capture“environment”= — phones offer the camera straight away.
  • Resize. The raw shot (often several megapixels) is downscaled via <canvas> + drawImage to a 200-pixel longest side, then re-encoded at JPEG 0.85. Anything larger would balloon IndexedDB without buying recognition value at thumbnail size.

  • Edit. Opening edit prefills pendingImage from the existing row, so saving without picking a new file keeps the old photo.
  • Test hook. The rendered <img> carries alt={item.name}, which get_by_role("img", name…)= reads — semantic, no data-URL inspection. The fixture uses a 1×1 PNG: too small to be a real picture, enough to exercise load-resize-store-render end to end.

Without persistence the app is a toy — close the tab and the boxes vanish. The choice of TinyBase was sold partly on its built-in persisters; this is what makes that promise real.

  • Mechanism. The IndexedDB persister mirrors the store to a DB named organiser on every mutation. On the next boot, startAutoLoad reads it back into the store before the first render.
  • Where the code lives. In Initial load — this chapter is the what; that one is the how. No new code is earned here beyond the regression guard: a box that survives a reload.

Sync across devices

Persistence keeps the same device’s data across reloads. Sync goes one step further: the same data on multiple devices, plus a real server-side backup. The user opens the app on their phone, adds a box; the laptop, opened later, shows the same box; and a server pod restart doesn’t lose anything (cf. Sync server, Node side for the file-persister behind that guarantee).

  • Engine. TinyBase’s WebSocket synchronizer pairs with a small server-side counterpart; the client’s local store and the server keep each other in sync via row-level merge.
  • Opt-in. Sync is armed by visiting the app once with ?sync_url=ws://... in the query string. The URL is stashed in localStorage under organiser.sync_url and the parameter is stripped from the address bar so subsequent shares stay clean. Without the URL the app stays purely local — no surprise traffic.
  • Status indicator. A small role“status”= label in the app-bar surfaces off / connecting / connected / disconnected so the user knows whether their writes will leave the device.
  • App-ready first, sync after. data-app-ready is posted before sync starts. The user can interact during the connection — and if the server is unreachable, the app doesn’t hang waiting.

The server is a few lines of Node.js — it just relays the synchronizer protocol between connected clients (cf. Sync server, Node side for the source).

startSync reads the sync URL from the query (consumed once and stashed in localStorage so future opens still sync), opens the WebSocket, narrates state changes through setSyncStatus for the app-bar indicator, and hands the socket to TinyBase’s createWsSynchronizer for the protocol-level negotiation. Returns immediately if no URL is configured — the app stays purely local.

function setSyncStatus(s){
    const el = document.querySelector('[data-sync-status]');
    el.textContent = `Sync ${s}`;
    el.dataset.status = s;
}

async function startSync(){
    const params = new URLSearchParams(location.search);
    const fromParam = params.get('sync_url');
    if(fromParam){
        localStorage.setItem('organiser.sync_url', fromParam);
        const clean = new URL(location);
        clean.searchParams.delete('sync_url');
        history.replaceState(null, '', clean);
    }
    const syncUrl = localStorage.getItem('organiser.sync_url');
    if(!syncUrl){ setSyncStatus('off'); return; }
    console.log('[sync] opening', syncUrl);
    setSyncStatus('connecting');
    const ws = new WebSocket(syncUrl);
    ws.addEventListener('open', () => { console.log('[sync] open'); setSyncStatus('connected'); });
    ws.addEventListener('close', e => { console.log('[sync] close', e.code, e.reason); setSyncStatus('disconnected'); });
    ws.addEventListener('error', e => { console.log('[sync] error', e); setSyncStatus('disconnected'); });
    const sync = await createWsSynchronizer(store, ws);
    await sync.startSync();
}

Sync server, Node side

  • Image. Packaged as konubinix/tinybasesync:0.1.1 via the user’s nomad/docker/Earthfile — same pattern as Condorcet’s automergesync. Build with clk nd build tinybasesync and push once; the test fixture and the nomad job pull from the registry.
  • Runtime. Bun (not node), because TinyBase’s peerOptional fanout (electric-sql, react, react-native…) is internally inconsistent and trips npm’s strict resolver. Bun resolves peer optionals lazily and runs .mjs directly.
  • Server-side persistence. Each path-room gets a TinyBase MergeableStore mirrored to a JSON file under $DATA_DIR via createFilePersister. The file is loaded on first connection and saved on every change. A pod restart recovers all rooms from disk — the server is a real backup, not just a relay.
  • Sources. server.mjs and package.json live in nomad/docker/tinybasesync/, COPY’d by the Earthfile into the image.

Store schema

Two tables.

  • boxes keyed by id:
    • photo — JPEG data-URL thumbnail (the only thing the user sees of a box).
    • photoName — file basename, used as accessible label and as the test hook.
    • order — integer used to sort the list (cf. Reorder boxes).
  • items keyed by id:
    • name — the item’s identity to the user.
    • boxId — empty when unassigned (cf. Drop an item into a box).
    • image — optional JPEG data-URL thumbnail (cf. Items with photos).

boxes: {
  <id>: { photo: string, photoName: string, order: number }
}
items: {
  <id>: { name: string, boxId: string, image: string }
}

Initial load

At boot:

  1. Create the store and bind an IndexedDB persister (rationale in Persistence).
  2. await persister.startAutoLoad() — replays the stored state.
  3. Wire store.addTablesListener(render).
  4. Call render() once.
  5. await persister.startAutoSave() — every later mutation hits IndexedDB.
  6. Set data-app-ready — tests’ single “ready to drive” signal.

Order matters. If the listener were wired before startAutoLoad, render would fire on every replay-write and burn the first paint on partial states. Listener-after-load means render runs once, on the final loaded state.

import { createMergeableStore } from 'tinybase';
import { createIndexedDbPersister } from 'tinybase/persisters/persister-indexed-db';
import { createWsSynchronizer } from 'tinybase/synchronizers/synchronizer-ws-client';

// MergeableStore (not the plain Store) is what the WS synchronizer
// requires — it carries the per-cell HLC timestamps that make
// conflict-free merges possible across devices.
const store = createMergeableStore();
const persister = createIndexedDbPersister(store, 'organiser');

function render(){
  const noBoxes = !Object.keys(store.getTable('boxes')).length;
  const noItems = !Object.keys(store.getTable('items')).length;
  document.querySelector('[data-empty-state]').hidden = !(noBoxes && noItems);
  const list = document.querySelector('[data-boxes-list]');
  const rows = store.getTable('boxes');
  const itemsById = store.getTable('items');
  const queryB = (document.querySelector('[data-search]')?.value || '').trim().toLowerCase();
  const itemMatchesB = name => !queryB || name.toLowerCase().includes(queryB);
  const sortedIds = Object.keys(rows).sort((a, b) =>
      (rows[a].order ?? 0) - (rows[b].order ?? 0));
  const ids = sortedIds.filter(id => {
      if(!queryB) return true;
      return Object.keys(itemsById).some(iid =>
          itemsById[iid].boxId === id && itemMatchesB(itemsById[iid].name));
  });
  list.hidden = !ids.length;
  list.replaceChildren(...ids.map((id, idx) =>
      renderBoxEl(id, idx, rows[id], itemsById, itemMatchesB)));
  const unassignedSection = document.querySelector('[data-unassigned]');
  const unassignedList = document.querySelector('[data-unassigned-items]');
  const itemsTable = store.getTable('items');
  const queryU = (document.querySelector('[data-search]')?.value || '').trim().toLowerCase();
  const unassignedIds = Object.keys(itemsTable).filter(id => {
      if(itemsTable[id].boxId) return false;
      return !queryU || itemsTable[id].name.toLowerCase().includes(queryU);
  });
  unassignedSection.hidden = !unassignedIds.length;
  unassignedList.replaceChildren(...unassignedIds.map(id =>
      renderItemEl(id, itemsTable[id])));
}

PWA shell

The PWA shell is what makes the app installable on a phone home screen and usable offline. Three pieces:

  • Manifest — the OS-level identity of the app: name, theme color, icon, display: standalone (no browser chrome).
  • Service worker — cache-first + write-through. First visit populates the cache from the network; later visits open instantly and survive offline. The cache name carries a build hash, so a tangle that changes any build artifact retires the old cache automatically.
  • Loading ring — a fullscreen spinner shown while the ESM imports and the persister load are in flight. Hidden the moment the body gets data-app-ready. Avoids the empty-page flash on cold start.

The manifest icon is an inline SVG data-URL — keeps everything in one file, no separate icon asset to track.

Playwright tests

Tests touch only what the user sees: visible text, ARIA roles, labels, placeholders. No store inspection, no test-only hooks, no implementation selectors. A test coupled to internals breaks on every refactor and stops being a contract.

Tests are scattered through the doc next to each feature, but the runner needs to call them all. A central list would be fragile — a test added but forgotten there shows up only at the next regression. The @testcase decorator is the registration point: defining a function with @testcase adds it to TESTS in source order.

TESTS = []

def testcase(fn):
    """Registration decorator: each =@testcase= pushes the function
    into =TESTS= in definition order."""
    TESTS.append(fn)
    return fn

Each test starts from a clean state. Without it, the IndexedDB of the previous test leaks ghost rows, and localStorage drafts resurface at reload — enough for tests to interfere with each other.

Cross-context tests need two isolated browser contexts (each with its own IndexedDB and localStorage) so we can simulate two devices syncing through the server. open_app goes to a URL and waits for the data-app-ready signal, in any context.

from contextlib import contextmanager

def open_app(ctx, url):
    page = ctx.new_page()
    page.set_default_timeout(5000)
    page.goto(url, timeout=15000)
    page.wait_for_selector("[data-app-ready]", timeout=15000)
    return page

@contextmanager
def two_contexts(browser):

    ctxB = browser.new_context(viewport={"width": 400, "height": 800})

Sync tests need the server up. require_sync_server is lazy and cached: the first call docker run’s the published image (cf. Sync server, Node side); subsequent calls reuse the same container. Cleanup is registered with atexit so the runner stops the container once at the end, not per-test. Same shape as Condorcet’s require_sync_server.

import atexit
import shutil
import socket
import subprocess
import time

SYNC_IMAGE = "konubinix/tinybasesync:0.1.1"
_SYNC_STATE = {"container": None, "url": None}

def _free_port():
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
        s.bind(("127.0.0.1", 0))
        return s.getsockname()[1]

def _wait_port(port, timeout=20.0):
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        try:
            with socket.create_connection(("localhost", port), timeout=0.5):
                return True
        except OSError:
            time.sleep(0.2)
    return False

def require_sync_server():
    if _SYNC_STATE["url"]:
        return _SYNC_STATE["url"]
    if not shutil.which("docker"):
        raise RuntimeError("docker not found — required for sync tests")
    port = _free_port()
    container = f"organiser-sync-{uuid.uuid4().hex[:8]}"
    try:
        subprocess.check_call(
            ["docker", "run", "-d", "--rm", "--name", container,
             "-p", f"127.0.0.1:{port}:8044",
             SYNC_IMAGE],
            stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL,
        )
    except subprocess.CalledProcessError as e:
        raise RuntimeError(
            f"docker run {SYNC_IMAGE} failed — has the image been built "
            f"and published? See the Earthfile target in [Sync server, "
            f"Node side]."
        ) from e
    if not _wait_port(port):
        subprocess.run(["docker", "stop", container],
                       stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
        raise RuntimeError(f"sync server didn't respond on :{port}")
    _SYNC_STATE["container"] = container
    _SYNC_STATE["url"] = f"ws://localhost:{port}"
    return _SYNC_STATE["url"]

@atexit.register
def _cleanup_sync():
    c = _SYNC_STATE.get("container")
    if c:
        subprocess.run(["docker", "stop", c],
                       stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)

The runner takes positional patterns (substring of test name, OR-matched) and a -x flag to stop on the first red — ./organiser.py empty, ./organiser.py -x, ./organiser.py --headed to see the browser. With no argument, the whole suite runs.

def main():
    argv = sys.argv[1:]
    headed = "--headed" in argv
    stop_on_fail = "-x" in argv or "--exitfirst" in argv
    patterns = [a for a in argv
                if a not in ("--headed", "-x", "--exitfirst")]
    selected = [t for t in TESTS
                if not patterns or any(p in t.__name__ for p in patterns)]
    if not selected:
        print(f"no test matches {patterns}")
        sys.exit(2)
    with sync_playwright() as pw:
        browser = pw.chromium.launch(headless=not headed)
        ctx = browser.new_context(viewport={"width": 400, "height": 800})
        page = ctx.new_page()
        page.set_default_timeout(5000)
        passed = failed = 0
        for t in selected:
            try: t(page); passed += 1
            except Exception as e:
                print(f"  FAIL: {t.__name__}: {e}"); failed += 1
                if stop_on_fail: break
        browser.close()
        print(f"\n{passed} passed, {failed} failed out of {len(selected)}")
        sys.exit(1 if failed else 0)

if __name__ == "__main__":
    main()
