Frise Chrono

Fleeting

I have years of photos and videos sitting in Postgres, exposed through PostgREST (the ipfsdocs slider reads them). The slider walks them one at a time; what I miss is the shape of time — seeing a whole stretch of months at once, each photo pinned where it actually happened, the way a wall timeline reads at a glance.

Let’s build that frise: a horizontal time ruler with month and year graduations, photos posed by date above it.

Choice of technology

My last local-first app, the organiser, leaned on TinyBase because its data was born on the device and had to merge across phones — a job for a CRDT. The frise is the opposite case. The photos already live in Postgres; the database is the source of truth, and the app only reads it (the rare write — tagging, changing a state — is a fire-and-forget that invalidates a cache, not a concurrent edit to reconcile). No CRDT, no local store to keep in step with a remote one.

That reframes the lesson I took from the organiser. The trap there was never “two engines” as such — it was the hand-written bridge between a render engine and a CRDT, kept in sync by code I had to maintain. Two engines are fine when the bridge between them ships with the libraries and the data flows one way. A read-mostly app is exactly that setting: data comes down, events go up, nothing merges.

So I get to try a fresh combo, picked so the bridge is off-the-shelf:

  • PostGraphile exposes the same Postgres as a GraphQL API — the experiment I want to run alongside the existing PostgREST.
  • urql is a small GraphQL client whose normalised cache is the read store: PostGraphile fills it, the UI reads from it. Its Preact bindings are the bridge I don’t have to write.
  • Preact + HTM render with hooks and JSX-like tagged templates — no build step, loaded straight from esm.sh through an import map.

The frise itself — the ruler, the month and year ticks, the photos placed by date — stays a bespoke component on plain CSS. A timeline library would drag in its own DOM and its own data model: a second store to reconcile with urql’s, the hand-written bridge again, for a layout that is a few lines of date → x.

Boot into a titled shell

Before a single photo has loaded, the screen must not read as broken. The minimum honest boot is a titled shell: the app mounts and names itself, so an empty screen says “the frise, still loading” rather than “nothing happened”. The loading and empty states proper come once there is a backend to be loading from; this first cycle only pins that the shell mounts and shows its name.

The test opens the app and looks for the title by its heading role — the observable surface, stable across every later state the frise will grow.

@testcase
def test_boots_into_titled_shell(page):
    """Opening the app shows the titled shell, so a blank screen never
    reads as broken."""
    open_app(page)
    assert page.get_by_role("heading", name="Frise chrono").is_visible(), \
        "the app title isn't visible after load"
    print("  PASS: boots into titled shell")

Booting needs two things in the page: an import map naming where the render libraries come from, and a node to mount into. The map carries only what this cycle uses — Preact’s html and render, bound together by HTM; the GraphQL client earns its entry when the first query does.

<script type="importmap">
  {
    "imports": {
      "htm/preact": "https://esm.sh/htm@3/preact"
    }
  }
</script>


<div id="app"></div>

The boot itself renders the shell and raises a data-app-ready flag on the body, so the test waits on a deterministic signal rather than a guessed delay.

import { html, render } from 'htm/preact';

function App(){
    return html`<h1>Frise chrono</h1>`;
}

render(html`<${App} />`, document.getElementById('app'));
document.body.setAttribute('data-app-ready', '1');

A dark canvas under it all, so the shell doesn’t flash white before the styles settle.

:root{ --bg:#1b1d2e; --fg:#e8e8f0; }
body{ background:var(--bg); color:var(--fg); font-family:system-ui,sans-serif; margin:0; }
