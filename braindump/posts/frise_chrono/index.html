Frise Chrono

Fleeting

I have years of photos and videos sitting in Postgres, exposed through PostgREST (the ipfsdocs slider reads them). The slider walks them one at a time; what I miss is the shape of time — seeing a whole stretch of months at once, each photo pinned where it actually happened, the way a wall timeline reads at a glance.

Let’s build that frise: a horizontal time ruler with month and year graduations, photos posed by date above it.

Choice of technology

My last local-first app, the organiser, leaned on TinyBase because its data was born on the device and had to merge across phones — a job for a CRDT. The frise is the opposite case. The photos already live in Postgres; the database is the source of truth, and the app only reads it (the rare write — tagging, changing a state — is a fire-and-forget that invalidates a cache, not a concurrent edit to reconcile). No CRDT, no local store to keep in step with a remote one.

That reframes the lesson I took from the organiser. The trap there was never “two engines” as such — it was the hand-written bridge between a render engine and a CRDT, kept in sync by code I had to maintain. Two engines are fine when the bridge between them ships with the libraries and the data flows one way. A read-mostly app is exactly that setting: data comes down, events go up, nothing merges.

So I get to try a fresh combo, picked so the bridge is off-the-shelf:

  • PostGraphile exposes the same Postgres as a GraphQL API — the experiment I want to run alongside the existing PostgREST.
  • urql is a small GraphQL client whose normalised cache is the read store: PostGraphile fills it, the UI reads from it. Its Preact bindings are the bridge I don’t have to write.
  • Preact + HTM render with hooks and JSX-like tagged templates — no build step, loaded straight from esm.sh through an import map.

The frise itself — the ruler, the month and year ticks, the photos placed by date — stays a bespoke component on plain CSS. A timeline library would drag in its own DOM and its own data model: a second store to reconcile with urql’s, the hand-written bridge again, for a layout that is a few lines of date → x.

Boot into a titled shell

Before a single photo has loaded, the screen must not read as broken. The minimum honest boot is a titled shell: the app mounts and names itself, so an empty screen says “the frise, still loading” rather than “nothing happened”. The loading and empty states proper come once there is a backend to be loading from; this first cycle only pins that the shell mounts and shows its name.

The test opens the app and looks for the title by its heading role — the observable surface, stable across every later state the frise will grow.

The shell owns the window state — opening on the last month — and hands it to the controls, the photos, and the ruler. Writes come back up through onChange; reads go down. The query bounds are the window with from clamped to MIN_DATE, so the floor holds however far back the viewer scrolls. Every change mirrors into the URL (?from=&to=) and the initial state is read back from there, so a view is shareable and survives a reload. One loop, no component drives itself.

const isoDay = ms => new Date(ms).toISOString().slice(0, 10);
const defaultWin = () => ({ from: isoDay(Date.now() - 31 * DAY), to: isoDay(Date.now()) });
const winFromUrl = () => {
    const p = new URLSearchParams(location.search);
    const from = p.get('from'), to = p.get('to');
    return (from && to) ? { from, to } : null;
};
function App(){
    const [win, setWin] = useState(() => winFromUrl() || defaultWin());
    const [open, setOpen] = useState(null);
    const update = w => {
        setWin(w);
        try { history.replaceState(null, '', `?from=${w.from}&to=${w.to}`); } catch (e) {}
    };
    const vars = { from: win.from > MIN_DATE ? win.from : MIN_DATE, to: win.to, search: win.search };
    return html`
      <h1>Frise chrono</h1>
      <${SearchBox} win=${win} onChange=${update} />
      <${WindowControls} win=${win} onChange=${update} onReset=${() => update(defaultWin())} />
      <${PanSlider} win=${win} onChange=${update} />
      <${PhotoCount} win=${vars} />
      <${TimelineStrip} win=${vars} onOpen=${setOpen}
        onZoom=${(frac, dy) => update(zoomAt(vars, frac, dy))} />
      <${Ruler} win=${vars} onZoom=${(a, b) => update({ from: isoDay(a), to: isoDay(b) })} />
      <${Loading} win=${vars} />
      <${EmptyHint} win=${vars} />
      <${Lightbox} key=${open ? open.cid : 'none'} doc=${open} onClose=${() => setOpen(null)} />
    `;
}

Photos land on the axis

The shell is honest but empty. Time to bring in the real photos. They live in Postgres and reach us as GraphQL through PostGraphile v5 at http://home/graphql, each carrying a date and a thumbnailCid. The frise’s whole promise is that a photo sits where it happened — so the first thing to pin down is position follows time: read left to right, the thumbnails march forward in date order.

The test hardcodes no pixel and no particular photo — the data is live. The thumbnails are rendered in date order (the query asks for DATE_ASC), so the property to pin is simply that their horizontal positions, read in document order, never go backwards. If two photos swap, the axis is lying about time.

@testcase
def test_photos_positioned_by_date(page):
    """Thumbnails (rendered in date order) have non-decreasing left positions."""
    open_app(page)
    page.wait_for_selector("[data-photo-date]")
    xs = page.eval_on_selector_all(
        "[data-photo-date]",
        "els => els.map(e => e.getBoundingClientRect().left)")
    assert len(xs) >= 2, "expected several photos on the axis"
    assert xs == sorted(xs), \
        "photos are not laid out left-to-right in date order"
    print("  PASS: photos positioned by date")

One query feeds everything, parameterized by the window — a from=/=to pair of dates. It returns the first 300 photos in the range, in date order. MIN_DATE is the floor the window opens at, so placeholder rows (motivated in Only real dates) never enter. We can’t filter on thumbnailCid (only indexed columns are filterable, and it isn’t one), so missing-thumbnail rows are dropped in the component instead.

const MIN_DATE = '2007-01-01';
const PHOTOS = `
  query Photos($search: String!, $since: Datetime!, $until: Datetime!) {
    photovideosSearch(search: $search, since: $since, until: $until, first: 300) {
      totalCount
      nodes { cid date thumbnailCid webCid mimetype filename size cameraType labels }
    }
  }
`;

Every component reads through one hook so the query, its variables and the thumbnail filter live in a single place. An empty search means “everything in the window”; a term narrows it — the window (since=/=until) and date order come from the server function either way.

function usePhotos(win){
    const [res] = useQuery({ query: PHOTOS, variables: {
        search: (win.search || '').trim(), since: win.from, until: win.to,
    } });
    const conn = res.data?.photovideosSearch;
    return {
        nodes: (conn?.nodes ?? []).filter(n => n.thumbnailCid),
        total: conn?.totalCount ?? 0,
        fetching: res.fetching,
    };
}

The client points at PostGraphile; a thumbnail base turns each /ipfs/... path into a loadable URL (both live on the same host as the GraphQL endpoint).

The strip maps time to space across the window: win.from and win.to are the two ends, and each thumbnail sits at its date’s fraction of that span — left as a percentage, centred on the point. The data-photo-date attribute is the seam the test reads, and data-kind (photo or video, from the mimetype) lets a video wear a distinct ring. Clicking a thumbnail opens its full media (see Open a photo).

function TimelineStrip({ win, onOpen, onZoom }){
    const { nodes } = usePhotos(win);
    const ref = useRef();
    const [w, setW] = useState(0);
    useLayoutEffect(() => {
        const el = ref.current;
        if(!el) return;
        const measure = () => setW(el.clientWidth);
        measure();
        const ro = new ResizeObserver(measure);
        ro.observe(el);
        return () => ro.disconnect();
    }, []);
    const min = new Date(win.from).getTime(), span = (new Date(win.to).getTime() - min) || 1;
    const placed = assignLanes(nodes, min, span, w);
    const lanes = placed.reduce((m, p) => Math.max(m, p.lane), 0) + 1;
    return html`
      <div class="strip" ref=${ref} style=${`height:${nodes.length ? lanes * ROW : 0}px`}
           onWheel=${e => { if(!e.shiftKey) return; e.preventDefault();
                            const r = e.currentTarget.getBoundingClientRect();
                            onZoom((e.clientX - r.left) / r.width, e.deltaY); }}>
        ${placed.map(({ n, lane }) => html`
          <img class="pin" data-photo-date=${n.date} title=${n.date.slice(0, 10)}
               data-kind=${(n.mimetype || '').startsWith('video') ? 'video' : 'photo'}
               style=${`left:${xLeft((new Date(n.date).getTime() - min) / span)}; top:${lane * ROW}px`}
               src=${THUMB_BASE + n.thumbnailCid}
               onClick=${() => onOpen(n)} />
        `)}
      </div>
    `;
}

A relative strip with the thumbnails absolutely placed along it, each centred on its date by a half-width shift. The thumbnails are a uniform size: with a fixed width the half-width shift is constant, so two photos sharing a date (there are many — missing dates default to a sentinel) land at exactly the same spot rather than wobbling by their differing aspect ratios.

A ruler that follows the span

Thumbnails strung along an invisible line read as a pile, not a timeline. What makes it a frise is the ruler underneath — graduations the eye anchors to. The graduation has to follow whatever span is on screen: years across decades, months across a year, days across a week — one ruler, relabelled. And it must stay robust for any span (the current window, once dated photos are floored, can be as tight as a handful of seconds), so the ruler lays a fixed number of evenly-spaced marks across the range and labels each at the unit the span calls for.

The test pins that the marks exist, in order, climbing left to right.

@testcase
def test_ruler_in_order(page):
    """The ruler's marks are laid out left-to-right across the span."""
    open_app(page)
    page.wait_for_selector("[data-tick]")
    xs = page.eval_on_selector_all(
        "[data-tick]", "els => els.map(e => e.getBoundingClientRect().left)")
    assert len(xs) >= 2, "expected several ruler marks"
    assert xs == sorted(xs), "ruler marks are not in left-to-right order"
    print("  PASS: ruler in order")

A label formatter picks the unit from the span: the year for multi-year ranges, the month for multi-month, the day for multi-day, the time below that.

const MONTHS = ['Jan','Feb','Mar','Apr','May','Jun','Jul','Aug','Sep','Oct','Nov','Dec'];
const DAY = 864e5, YEAR = 365.25 * DAY;
function tickLabel(t, span){
    const d = new Date(t);
    if(span >= 2 * YEAR) return String(d.getFullYear());
    if(span >= 60 * DAY)  return `${MONTHS[d.getMonth()]} ${d.getFullYear()}`;
    if(span >= 2 * DAY)   return `${d.getDate()} ${MONTHS[d.getMonth()]}`;
    return `${String(d.getHours()).padStart(2,'0')}:${String(d.getMinutes()).padStart(2,'0')}`;
}

The ruler is its own component reading the same query — urql serves it from cache, so there’s no second round-trip; it only needs the photos to know whether the window is empty. It spans the same window and lays a mark on each calendar boundary within it; rendered full width under the photos, the marks line up with the thumbnails above. Clicking a mark zooms the window to the interval it opens — from that boundary to the next.

function Ruler({ win, onZoom }){
    const { nodes } = usePhotos(win);
    if(nodes.length === 0) return '';
    const min = new Date(win.from).getTime(), max = new Date(win.to).getTime(), span = (max - min) || 1;
    const ticks = niceTickTimes(min, max);
    return html`
      <div class="ruler">
        ${ticks.map((t, i) => html`
          <span class="tick" data-tick="" style=${`left:${((t - min) / span) * 100}%`}
                onClick=${() => onZoom(t, ticks[i + 1] ?? max)}>${tickLabel(t, span)}</span>
        `)}
      </div>
    `;
}

The band is a thin blue strip; each label sits absolutely at its fraction, centred on the year boundary.

Only real dates

The earliest photos are almost all placeholders: rows whose date was never set land on epoch defaults (1970-01-01, 1999-01-01=…) and pile up at the left edge, crowding out anything real and stretching the whole scale back to 1970. The [[id:6b5e4704-44dd-4764-b4f0-fb5606a13c6c][slider]] already drew a line here — its date picker floors at =2007-01-01 — so the frise adopts the same floor and asks the database for dated photos only. The filter is server-side on the indexed date column, so it costs nothing.

The test pins that no photo older than the floor reaches the strip.

A window you can move

Three hundred photos out of seventy-five thousand is a peephole. To roam the archive the frise needs a window — a from/to pair the viewer sets — and the query fetches only what falls inside it. The date column is indexed, so a bounded range is cheap, and the ruler we already built relabels itself as the window tightens from years to months to days.

The test moves the window to a single month and checks the frise answers with photos from that month only.

@testcase
def test_window_narrows(page):

The window is a from=/=to pair of dates. Two date inputs read and write it; editing either reports the new pair upward, which is all the controls do — the state itself lives in the app root. The data-win-* attributes are the seams the test drives.

function WindowControls({ win, onChange, onReset }){
    const shift = dir => {
        const f = new Date(win.from).getTime(), t = new Date(win.to).getTime(), span = (t - f) || DAY;
        onChange({ from: isoDay(f + dir * span), to: isoDay(t + dir * span) });
    };
    return html`
      <div class="controls">
        <button type="button" data-prev onClick=${() => shift(-1)}>‹ prev</button>
        <label>from <input type="date" data-win-from value=${win.from}
          onInput=${e => { const f = e.target.value; onChange({ from: f, to: f > win.to ? f : win.to }); }} /></label>
        <label>to <input type="date" data-win-to value=${win.to}
          onInput=${e => { const t = e.target.value; onChange({ from: t < win.from ? t : win.from, to: t }); }} /></label>
        <button type="button" data-next onClick=${() => shift(1)}>next ›</button>
        <button type="button" data-reset onClick=${onReset}>reset</button>
      </div>
    `;
}

The window is the scale

A subtle wrong turn so far: the photos and the ruler scale to the fetched photos’ own earliest and latest dates, so any batch — even 300 photos from a single month — stretches edge to edge. The honest scale is the window itself: a photo from the start of a ten-year window belongs near the left, not splashed across the whole strip. So both layers measure against win.from=/=win.to.

The test opens a ten-year window; the earliest photos (all near its start) must sit in the left portion, not span the width.

@testcase
def test_window_is_the_scale(page):
    """Photos map onto the window, not onto their own sub-range."""
    open_app(page)
    page.wait_for_selector("[data-photo-date]")
    page.fill("[data-win-from]", "2010-01-01")
    page.fill("[data-win-to]", "2020-01-01")
    page.wait_for_function(
        "() => { const ds = [...document.querySelectorAll('[data-photo-date]')];"
        " return ds.length > 0 && ds.every(e => { const d = e.getAttribute('data-photo-date');"
        " return d >= '2010-01-01' && d <= '2020-01-01'; }); }")
    xs = page.eval_on_selector_all("img.pin", "els => els.map(e => e.getBoundingClientRect().left)")
    width = page.eval_on_selector(".strip", "el => el.getBoundingClientRect().width")
    assert xs, "no photos in window"
    assert max(xs) < width * 0.5, \
        "early-window photos stretch across the whole strip — scale isn't the window"
    print("  PASS: window is the scale")

Ticks on real boundaries

Evenly-spaced marks read oddly: across a quarter you get Jun · Jun · Jul · Jul · Aug · Sep, the same month labelled twice because two marks fell inside it. A ruler should land on the boundaries themselves — the first of each month, the first of each year — so every label is a real, distinct graduation, the way your reference photo’s Oct Nov Dec sit on month starts.

The test moves to a three-month window, where evenly-spaced marks would repeat a month, and demands every label be distinct.

@testcase
def test_ticks_on_real_boundaries(page):
    """Each tick is a distinct calendar boundary — no repeated labels."""
    open_app(page)
    page.wait_for_selector("[data-tick]")
    page.fill("[data-win-from]", "2015-06-01")
    page.fill("[data-win-to]", "2015-09-01")
    page.wait_for_function(
        "() => { const ds = [...document.querySelectorAll('[data-photo-date]')];"
        " return ds.length > 0 && ds.every(e => e.getAttribute('data-photo-date').startsWith('2015')); }")
    labels = page.eval_on_selector_all("[data-tick]", "els => els.map(e => e.textContent)")
    assert len(labels) >= 2, "expected several ticks"
    assert len(labels) == len(set(labels)), \
        f"duplicate tick labels — not calendar-aligned: {labels}"
    print("  PASS: ticks on real boundaries")

The boundaries depend on the unit the span calls for — years (thinned to keep the count sane), months, days (likewise thinned), or hours. Each branch walks real calendar steps from the first boundary at or after min. If a span is so tight it holds fewer than two boundaries, the two ends stand in.

function niceTickTimes(min, max){
    const span = max - min, out = [];
    const add = t => { if(t >= min && t <= max) out.push(t); };
    if(span >= 2 * YEAR){
        const y0 = new Date(min).getFullYear(), y1 = new Date(max).getFullYear();
        const step = Math.max(1, Math.ceil((y1 - y0 + 1) / 10));
        for(let y = Math.ceil(y0 / step) * step; y <= y1; y += step) add(new Date(y, 0, 1).getTime());
    } else if(span >= 60 * DAY){
        const d = new Date(min); d.setDate(1); d.setHours(0, 0, 0, 0);
        if(d.getTime() < min) d.setMonth(d.getMonth() + 1);
        for(; d.getTime() <= max; d.setMonth(d.getMonth() + 1)) add(d.getTime());
    } else if(span >= 2 * DAY){
        const step = Math.max(1, Math.ceil(span / DAY / 10));
        const d = new Date(min); d.setHours(0, 0, 0, 0);
        if(d.getTime() < min) d.setDate(d.getDate() + 1);
        for(; d.getTime() <= max; d.setDate(d.getDate() + step)) add(d.getTime());
    } else {
        const d = new Date(min); d.setMinutes(0, 0, 0);
        if(d.getTime() < min) d.setHours(d.getHours() + 1);
        for(; d.getTime() <= max; d.setHours(d.getHours() + 1)) add(d.getTime());
    }
    if(out.length < 2){ out.length = 0; add(min); add(max); }
    return out;
}

Open on the recent past

When the query returns nothing, a quiet line takes the strip’s place. It reads the same cached query and only speaks once the fetch has settled, so it never flashes during loading.

function EmptyHint({ win }){
    const { nodes, fetching } = usePhotos(win);
    if(fetching) return '';
    return nodes.length === 0 ? html`<p class="empty" data-empty>No photos in this window.</p>` : '';
}

How many are in the window

The strip shows at most three hundred thumbnails, but a year holds thousands. A reader staring at a packed strip can’t tell whether they’re seeing everything or a slice. A count settles it — the total in the window, and a note when only the first three hundred are drawn.

The test opens a year known to hold thousands and reads the total back.

function Lightbox({ doc, onClose }){
    const [labels, setLabels] = useState(doc?.labels || '');
    const [, runSet] = useMutation(SET_LABELS);
    if(!doc) return '';
    const phrases = labels.split(',').map(s => s.trim()).filter(Boolean);
    const save = next => { const s = next.join(', '); setLabels(s); runSet({ cid: doc.cid, labels: s }); };
    const add = w => { w = w.trim(); if(w && !phrases.includes(w)) save([...phrases, w]); };
    const rows = [
        ['date', doc.date && doc.date.slice(0, 19).replace('T', ' ')],
        ['file', doc.filename],
        ['type', doc.mimetype],
        ['size', doc.size && `${Math.round(doc.size / 1024)} KB`],
        ['camera', doc.cameraType],
    ].filter(([, v]) => v);
    const url = THUMB_BASE + (doc.webCid || doc.thumbnailCid);
    return html`
      <div class="lightbox" data-lightbox onClick=${onClose}>
        <div class="lightbox-inner" onClick=${e => e.stopPropagation()}>
          <img src=${url} />
          <div class="side">
            <div class="labels">
              ${phrases.map(p => html`<span class="label" data-label>${p}
                <button onClick=${() => save(phrases.filter(x => x !== p))}>×</button></span>`)}
            </div>
            <input class="label-add" data-label-add placeholder="add label + Enter"
                   onKeyDown=${e => { if(e.key === 'Enter'){ add(e.currentTarget.value); e.currentTarget.value = ''; } }} />
            <dl class="meta">
              ${rows.map(([k, v]) => html`<div data-meta><dt>${k}</dt><dd>${v}</dd></div>`)}
            </dl>
            <a class="raw" target="_blank" href=${url} target="_blank">open original ↗</a>
          </div>
        </div>
      </div>
    `;
}

        ".map(e => Math.round(e.getBoundingClientRect().top))).size > 1")

Lane assignment is greedy over the photos in date order: each one drops into the first lane whose last thumbnail has ended before this one’s left edge, or opens a new lane below if none has room. Because lanes need pixel positions, it takes the measured strip width w; before the width is known every photo sits in lane zero.

const THUMB = 64, GAP = 3, ROW = 70;
// shared date→x mapping: inset half a thumbnail each side so edges aren't clipped.
// assignLanes and the rendered left MUST use this same inset or overlap detection drifts.
const xLeft = frac => `calc(${frac} * (100% - ${THUMB}px) + ${THUMB / 2}px)`;
function assignLanes(nodes, min, span, w){
    if(!w) return nodes.map(n => ({ n, lane: 0 }));
    const laneRight = [];
    return nodes.map(n => {
        const x = THUMB / 2 + ((new Date(n.date).getTime() - min) / span) * (w - THUMB);
        let lane = laneRight.findIndex(right => right <= x - THUMB / 2);
        if(lane === -1) lane = laneRight.length;
        laneRight[lane] = x + THUMB / 2 + GAP;
        return { n, lane };
    });
}

function PanSlider({ win, onChange }){
    const lo = new Date(MIN_DATE).getTime(), hi = Date.now();
    const f = new Date(win.from).getTime(), width = new Date(win.to).getTime() - f;
    const room = (hi - lo - width) || 1;

        const nf = lo + Number(e.target.value) * room;
        onChange({ from: isoDay(nf), to: isoDay(nf + width) });
    };

                       min="0" max="1" step="0.001" value=${pos} onInput=${onInput} />`;
}

function zoomAt(win, frac, deltaY){
    const f = new Date(win.from).getTime(), span = new Date(win.to).getTime() - f;
    const center = f + frac * span;

function SearchBox({ win, onChange }){
    const term = win.search || '';
    const [open, setOpen] = useState(false);
    const [{ data }] = useQuery({ query: COMPLETIONS, variables: { prefix: term }, pause: !term });
    const words = data?.labelCompletions?.nodes ?? [];
    const pick = w => { onChange({ ...win, search: w }); setOpen(false); };
    return html`
      <div class="searchbox">
        <input class="search" data-search type="search" placeholder="search labels…"
               value=${term}
               onInput=${e => { setOpen(true); onChange({ ...win, search: e.target.value }); }}
               onFocus=${() => setOpen(true)}
               onBlur=${() => setOpen(false)} />
        ${open && term && words.length ? html`
          <ul class="completions">
            ${words.map(w => html`<li class="completion" data-completion
                  onMouseDown=${e => { e.preventDefault(); pick(w); }}>${w}</li>`)}
          </ul>` : ''}
      </div>
    `;
}

Typing a prefix offers the labels already in use — drawn from labelCompletions — so you reuse a word rather than inventing a near-duplicate. Picking one fills the box.

@testcase
def test_label_completion(page):
    """Typing a prefix suggests matching labels; picking one fills the search."""
    open_app(page)
    page.fill("[data-search]", "cos")
    page.wait_for_selector("[data-completion]")
    items = page.eval_on_selector_all("[data-completion]", "els => els.map(e => e.textContent)")
    assert "cosmo" in items, f"expected a 'cosmo' suggestion, got {items}"
    first = page.locator("[data-completion]").first
    word = first.text_content()
    first.click()
    assert page.input_value("[data-search]") == word, "picking a suggestion didn't fill the search"
    print("  PASS: label completion")

Picking a suggestion must also close the dropdown — otherwise the query for the now-complete term returns it again and the list lingers, covering the controls below. The list opens while typing and closes on a pick or a blur.

@testcase
def test_completion_closes_after_pick(page):
    """Picking a completion closes the dropdown."""
    open_app(page)
    page.fill("[data-search]", "cos")
    page.wait_for_selector("[data-completion]")
    page.locator("[data-completion]").first.click()
    page.wait_for_selector("[data-completion]", state="detached")
    assert page.locator("[data-completion]").count() == 0, \
        "completion dropdown stayed open after a pick"
    print("  PASS: completion closes after pick")
