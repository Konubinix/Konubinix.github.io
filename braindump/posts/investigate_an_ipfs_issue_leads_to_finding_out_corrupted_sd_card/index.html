Investigate an Ipfs Issue Leads to Finding Out Corrupted Sd Card

Fleeting

Symptom

ipfs get bafybei… (a ~333 MiB DAG) on the requesting host hangs at exactly 113.16 MiB / 333.12 MiB (33.97%). The CID is “known to be on the private network” (4 RPi5 IPFS nodes, all installed from the same script).

Investigation

1. Bitswap state on the requesting node

ipfs bitswap stat

bitswap status
    blocks received: 4
    blocks sent: 0
    wantlist [1 keys]
        bafkreihdwdcefgh4dqkjv67uzcmw7ojee6xedzdetojuzjevtenxquvyku
    partners [0]

Hung waiting on a single raw block. Despite 4 swarm peers being connected (four hosts on the LAN, last-octet labels .1/.2/.3/.4), bitswap reports partners [0].

2. Per-peer bitswap ledgers

peer (ip) exchanges bytes received note
12D3KooWPus3 (.1) 3 14323 started serving, then stopped
12D3KooWCRRA (.2) 0 0 connected at libp2p, never bitswap
12D3KooWMFE2 (.3) 0 0 "
12D3KooWNPt4 (.4) 0 0 "

Routing.Type = none (DHT off, fine for private LAN). No swarm key. findprovs is therefore useless. The 5th “bootstrap” peer 12D3KooWKG85 is on the requesting host itself — a stale entry from a previous identity (different PeerID), harmless.

The user confirms: pinned the CID on >=2 nodes in the past, then unpinned. ipfs repo gc never runs (no --enable-gc in cmdline, GCPeriod=1500000h, StorageGCWatermark=90/2TB). So unpinned data should still be on disk.

3. node-1 (.1) logs

clk nd logs --job ipfs --node node-1 --stderr shows a Go runtime panic on every startup, in quic-go, on arm64:

exec ipfs daemon --migrate=true --enable-pubsub-experiment
INFO failed to sufficiently increase receive buffer size ...
runtime: pcdata is 7 and 5 locals stack map entries for
  github.com/quic-go/quic-go.(*outgoingStreamsMap[go.shape.*uint8]).OpenStream
fatal error: bad symbol table

Repeated across many supervisor restarts. The panic is in runtime.(*stkframe).getStackMap during copystack — classic symptom of an invalid pclntab / corrupted binary or memory.

4. Hash the binary inside the image

node sha256 of /usr/local/bin/ipfs version
node-2 456392265a6fea33fc457f37fbf2c9aa32680430c29215de3d716a3e148e01c9 0.39.0
node-1 fc63cb930b70066561db9cc475f23438f48abda4f8fb448bd6f566843e5d29c2 0.39.0

Different hashes for the same image tag. docker rmi --force + re-pull on node-1 produced fc63... again. So the image fetched into node-1’s docker storage is deterministically different from the one on node-2. The same tag in the registry is the same; docker image inspect would have settled which case applies, but the actual root cause was revealed by the next step.

5. Read-stability test on the binary

Storage layout on node-1:

  • root FS on SD card (/dev/mmcblk0p2, 14 GB)
  • Docker storage driver: overlay2 on extfs
  • Last ext4 fsck: Sat Aug 17 12:11:40 2024, mount count 84, state “clean”, errors-behavior “Continue”
  • dmesg/journal: no I/O errors (box was just rebooted today, ring buffer was empty)

Read the same on-disk file twice with the page cache flushed in between:

F=/var/lib/docker/overlay2/5f4262.../diff/usr/local/bin/ipfs
sha256sum "$F"                       # -> fc63cb93...
echo 3 > /proc/sys/vm/drop_caches
sha256sum "$F"                       # -> 931a207d...

Two different hashes for the same file in the same fs, no writes in between. The block device is returning different bytes on successive reads.

Root cause

The SD card on node-1 is silently corrupting reads (or has corrupted writes that now read back as random garbage). No kernel error, no ext4 error — just bit-flipping NAND. ext4 metadata_csum catches metadata corruption but file data has no checksum. Classic end-of-life SD card after a long stretch of Docker-style write load.

This explains the whole chain:

  • Go runtime panics with “bad symbol table” → the executable’s pclntab / itab data read back as random bytes.
  • docker rmi --force + re-pull doesn’t fix it → new bytes land on the same flaky NAND blocks (or the corruption is on read, not write).
  • Hash differs from node-2 → node-2’s SD reads its bytes correctly.
  • Same wrong hash twice in a row earlier in the session → page cache; flushing it surfaces the instability.
  • Why the network used to serve this CID and now doesn’t → node-1 is the (only?) node that has the leaf block; its daemon can no longer stay up to serve it.

Remediation

  1. Replace node-1’s SD card. Every read can return different garbage; nothing on it is trustworthy.
  2. Before replacing, attempt to rsync the ipfs blocks volume off node-1; corrupted blocks will be rejected by ipfs on the receiving side (CID mismatch) so we keep whatever survives.
  3. Verify on .2/.3/.4 whether any other node has the missing leaf block: 
    clk nd exec ipfs <node> -- ipfs block stat --offline \
  bafkreihdwdcefgh4dqkjv67uzcmw7ojee6xedzdetojuzjevtenxquvyku
    If yes, the current ipfs get can finish once node-1 stops poisoning the bitswap session, or with a one-shot ipfs swarm connect refresh after disabling node-1’s job.
  4. When replacing, pick a quality card — see Raspberry Pi SD Card (SanDisk A1 / Extreme Pro hold up under Pi workloads). USB-SSD or NVMe HAT remain the safest option for heavy write load.

Can the corrupted card be reused after reformatting?

Short answer: no, treat it as dead for any role you care about.

Reformatting only rewrites filesystem metadata. It does not reset the underlying NAND, does not restore the controller’s reserve blocks, and does not change which physical cells are flaky. What we observed — same file producing two different sha256 on successive reads — is the classic signature of NAND wear-out: the controller’s Flash Translation Layer (FTL) has run out of spare blocks to remap writes to, so reads now hit marginal cells that flip bits. The cells are degraded silicon; no software can fix that.

Less likely but possible alternatives, in decreasing order of plausibility for this card:

  • Counterfeit / fake-capacity card where writes past the real end wrap around and corrupt earlier sectors.
  • One-off voltage glitch or kernel driver bug (would not reproduce deterministically the way ours did).

Confirming wear-out (destructive)

Do this with the card in a USB reader on a different machine, not in the Pi. /dev/sdX must be carefully verified (lsblk first).

sudo umount /dev/sdX*

# f3: purpose-built SD validation; also catches fake capacity
sudo apt install f3
sudo f3probe --destructive --time-ops /dev/sdX
# then full write + read-back cycle on a fresh fs:
sudo f3write /mnt/sd
sudo f3read  /mnt/sd

# alternative: badblocks destructive write+read test
sudo badblocks -wsv -b 4096 /dev/sdX

A failed test (any reported corrupted sector / bad block) is definitive: card is dead, bin it.

Why a passing test does not certify the card

The asymmetry matters: failure proves bad, success proves nothing. The reasons are fundamental to flash, not limitations of the tools:

  • No predictive value. SD health is a function of future behaviour under the real workload — retention over weeks, wear progression under writes, bit-flip rate at temperature. No point-in-time test can predict that.
  • No telemetry exposed. Consumer SD cards have no SMART, no reserve-block count, no wear-level counter, no retention metric. The controller hides everything behind the FTL; you are testing a black box that reveals nothing about its remaining life.
  • Tests refresh what they touch. Destructive write+read tests rewrite every sector. The controller may remap them to known-good blocks, so the test reads back fresh data. Real-world use writes once and reads months later — that is when retention failures appear, and the test cannot simulate it within seconds.
  • Probabilistic flips are under-sampled. A marginal cell might flip 1 read in 1000. Single-pass tests miss this; sustained workload doesn’t.
  • Logical layer only. f3 / badblocks address LBAs. The FTL’s remap is opaque — the cells that misbehaved earlier may never be re-addressed during the test.

A retention soak (write, unpower for weeks, read back) under thermal/write stress matching the real workload would come closest, but even that only certifies the card up to that point.

Conclusion

The rule “definitive good, or drop it” collapses cleanly:

card state definitive verdict possible? action
brand new, unused yes — f3probe catches fakes / infant mortality run f3probe before deploying
in service, no symptoms no leave alone, monitor with scrub
in service, has shown bit-flips no — bad is definitive, “good” isn’t bin it

For node-1’s card: bit-flips observed → no test can recover it. Replace.

For replacement cards: see Raspberry Pi SD Card. Combined with the btrfs root + weekly btrfs scrub setup, the next failure will be loud and immediate instead of silent.

Periodic detection — nomad sysbatch sentinel

The cheapest reliable detector for the failure mode we hit is the same one that found it: read a static file twice with the page cache flushed between reads, alert on hash divergence. Add a 1 MiB write+read-back to also catch write-side rot.

Shape: type = "sysbatch" (one alloc per node) + periodic (cron-style schedule) + raw_exec (host-level, root, so it can write to /proc/sys/vm/drop_caches). Failure is signalled by a non-zero exit; nomad will surface it via clk nd status and the alloc’s stderr will contain the diagnostic line.

The name keeps sdrot even though the probe is media-agnostic: the SD card is the medium most likely to fail this way in this fleet, and the check still runs harmlessly on SSD/HDD-backed nodes.

job "sdrot" {
  datacenters = ["dc1"]
  type = "sysbatch"

  # Read-stability sentinel for the root filesystem. Detects silent
  # NAND bit-flips that ext4 cannot — same technique that caught the
  # node-1 failure.

  periodic {
    crons             = ["0 0 12 * * *"]
    prohibit_overlap = true
    time_zone        = "Europe/Paris"
  }

  group "sdrot" {
    ephemeral_disk {
      size = 50
    }
    task "sdrot" {
      logs {
        max_files     = 5
        max_file_size = 5
      }
      driver = "raw_exec"
      config {
        command = "${NOMAD_TASK_DIR}/sentinel.sh"
      }
      template {
        destination = "local/sentinel.sh"
        perms       = "755"
        data        = <<-EOH
        #!/bin/sh
        # Storage read-stability sentinel. Runs as root via raw_exec
        # because /proc/sys/vm/drop_caches needs write privilege.
        # Non-zero exit => nomad marks the alloc failed.
        set -u
        TARGET=/usr/lib/os-release

        # 1. Read-stability of a static system file.
        a=$(sha256sum "$TARGET" | awk '{print $1}')
        echo 3 > /proc/sys/vm/drop_caches
        b=$(sha256sum "$TARGET" | awk '{print $1}')
        if [ "$a" != "$b" ]; then
          echo "FAIL read-stability $TARGET: $a vs $b" >&2
          exit 1
        fi

        # 2. Write + read-back of 1 MiB random data (catches write-side rot).
        T=$(mktemp /var/tmp/sdrot.XXXXXX)
        trap 'rm -f "$T"' EXIT
        head -c 1048576 /dev/urandom > "$T"
        sync
        echo 3 > /proc/sys/vm/drop_caches
        expected=$(sha256sum "$T" | awk '{print $1}')
        echo 3 > /proc/sys/vm/drop_caches
        got=$(sha256sum "$T" | awk '{print $1}')
        if [ "$expected" != "$got" ]; then
          echo "FAIL write-readback: $expected vs $got" >&2
          exit 1
        fi
        EOH
      }
      resources {
        cpu    = 50
        memory = 30
      }
    }
  }
}

Lessons / pointers

  • partners [0] in ipfs bitswap stat, despite peers in swarm peers, means no peer currently has open bitswap sessions with us / acknowledges our wants. Always check this before blaming peers.
  • Routing.Type = "none" makes ipfs routing findprovs a no-op.
  • GC does not run automatically unless ipfs daemon --enable-gc and a threshold is exceeded — unpinning is not the same as deleting.
  • For SD-card silent corruption: do not trust dumpe2fs “clean”, do not trust dmesg quiet. Do a read-stability test with echo 3 > /proc/sys/vm/drop_caches between two reads of the same file. Differing hashes = storage is bad. This is also the cheapest fsck-equivalent for Docker on overlay2 (where layer blobs aren’t content-addressable on disk).
  • For Docker layer integrity, the in-disk story depends on the backend: overlay2 = extracted, not addressable; the containerd snapshotter keeps blobs content-addressed and can be fsck’d by recomputing each file’s sha256 vs its filename.
