objective

motivation
I configure my NixOS box from a versioned file; I want my phone’s home screen the same way — declared once, applied reproducibly, with no tapping, dragging or dropping.
question
on Android 7+ / LineageOS, can a home screen carrying several screens, app widgets, and PWAs — including self-hosted ones served from http://localhost — be provisioned declaratively from a version-controlled config, and at what privilege cost?
hypothesis
the target, held fixed for the whole note, is a de-Googled LineageOS — no Google Play Services (GMS) — running a Launcher3-based launcher — on stock LineageOS that is Trebuchet, a fork of AOSP’s Launcher31 — and a Chromium-based browser, on a device where root is at hand. A system-privileged step is therefore payable: the question stays what the privilege costs, not whether it can be paid.
[objective]: on a de-Googled LineageOS (Android 7+, no GMS, root at hand), can a home screen — several screens, app widgets and PWAs — be provisioned declaratively from a versioned file, with no manual tap/drag, and at what privilege cost?

can the home screen be described in a file?

claim
the workspace is expressible as data.
evidence
AOSP Launcher3 ships an XML parser whose vocabulary maps one-to-one onto screens, icons, folders, and widgets at chosen grid cells.

at what privilege does that file apply?

claim
expressible is not appliable.
tension
the XML’s source and read-time decide it: Launcher3 reads a resource baked into a system package, only once, not a user file.

why « add to home screen » is not enough for a PWA

claim
PWAs are the awkward third.
problem
the browser’s « add to home screen » does not yield an installed app on a de-Googled phone.
reason
the real install (a WebAPK) is minted by a Google server the phone cannot reach.

how to install a PWA declaratively

premise
the browser will not mint the app, so the app is built ahead of time, from a file.
mechanism
a Trusted Web Activity (TWA) wraps the PWA in a thin APK, and Bubblewrap generates that APK from the site’s web manifest.
claim
that is exactly IaC — config in, installable artifact out.

and a PWA served from http://localhost?

anomaly
one PWA does not fit the TWA path — the self-hosted one, served from the phone’s own loopback http://localhost, with no public domain and no certificate.
context
a Secure Context treats it as a securely-delivered, trustworthy origin2 — a verdict about the trust of the origin, distinct from Android’s Network Security Config, which still blocks cleartext to it by default; proving to a Trusted Web Activity that app and site share one owner is the trouble, since the site is every device’s own localhost.
fix
stop asking a Trusted Web Activity to trust a site it structurally cannot verify, and ship an app that never runs the check.
variant
the cleanest is our own thin WebView; forking the browser’s verification or decompiling a prebuilt TWA APK are heavier variants of the same bypass.

conclusion

answer
yes — as two mechanisms, not one: the launcher layout is expressible as declarative XML (a file) yet appliable only as a first-boot system artifact — root or a ROM build, plus a data wipe.
answer
PWAs cannot be installed by the browser without GMS (only a shortcut), so they take the TWA-from-manifest path — a versioned config compiled to an APK and adb install-ed.
answer
a http://localhost PWA is the exception to even that path — a Trusted Web Activity cannot verify a loopback origin, so it degrades to a URL-bar Custom Tab (the localhost case); the reproducible answer is our own thin WebView APK, not a TWA.
payoff
the no-tap/drag goal holds on both halves; the price is asymmetric — the PWA half is plain user-space tooling, the launcher half costs system privilege, payable on this target since root is at hand, though still at the price of a data wipe. See the overview map in the whole argument.
[iac feasible, split path]: home-screen-as-code is feasible on a de-Googled LineageOS, but along two distinct paths — the launcher layout as a first-boot system XML (root/ROM + data wipe), and PWAs as TWA APKs built from a versioned manifest and adb-installed. The no-tap/drag goal holds; only the launcher half costs system privilege. A =http://localhost= PWA is the one exception to the TWA route — it cannot pass Digital Asset Links verification, so it ships as our own WebView APK instead.
deferred
a user-space alternative for the launcher half — a third-party launcher whose backup/restore file can be generated and pushed without root (Nova, Lawnchair, others). With root assumed it is an optional simplification, not a necessity.
deferred
which LineageOS Chromium-based browsers implement the TWA protocol well enough to render a Bubblewrap APK full-screen.

the whole argument

scope
the overview carries the thesis, the two positive results that support it, and the privilege cost that qualifies it.
how

a worked example: the artifacts and the apply commands

scope
this chapter turns the conclusion into runnable artifacts — the launcher XML plus the TWA and WebView APKs — so the two paths are reproducible, not only proven.
step
declare the launcher layout as a system customization XML in AutoInstallsLayout’s vocabulary, then make it the first-boot source.
artifact
the workspace below places an icon, a two-app folder and a 2x1 widget on screens 0–1; its coordinates are the expressible layout (a file).

<?xml version="1.0" encoding="utf-8"?>
<workspace>
  <shortcut packageName="org.mozilla.fennec_fdroid"
            className="org.mozilla.fennec_fdroid.App"
            screen="0" x="0" y="0" />
  <folder title="@string/comms" screen="0" x="1" y="0">
    <shortcut packageName="org.thoughtcrime.securesms"
              className="org.thoughtcrime.securesms.RoutingActivity" />
    <shortcut packageName="org.signal"
              className="org.signal.RoutingActivity" />
  </folder>
  <appwidget packageName="com.nextcloud.client"
             className="com.nextcloud.client.widgets.ListWidgetProvider"
             screen="1" x="0" y="0" spanX="2" spanY="1" />
</workspace>
apply
ship that XML as a partner customization APK — a system package carrying the android.autoinstalls.config.action.PLAY_AUTO_INSTALL intent-filter, with the layout under res/xml/ — matching the first-boot loader (root or a ROM build, plus a data wipe).
command
install the overlay, then wipe the launcher so the loader re-runs on next boot: adb install custom-launcher-layout.apk, adb shell pm clear org.lineageos.trebuchet, adb reboot.
cost
the pm clear drops the launcher’s DB, so this is the first-boot-only, system-privilege cost the conclusion already named.
step
build each PWA as a TWA APK from its web manifest.
artifact
Bubblewrap reads the manifest and writes a versioned twa-manifest.json; the commands are config-in, artifact-out (the TWA path).

# init writes twa-manifest.json from the site's manifest
npx @bubblewrap/cli init \
  --manifest https://example.com/manifest.webmanifest \
  --packageId com.example.twa
# build emits app-release-signed.apk
npx @bubblewrap/cli build
# install on the device; a TWA-capable browser renders it
adb install app-release-signed.apk
apply
prove app and site share one owner via Digital Asset Links — host the file the browser fetches at first launch.

[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "com.example.twa",
      "sha256_cert_fingerprints": ["AA:BB:CC:DD:EE:FF"]
    }
  }
]
command
publish it at https://example.com/.well-known/assetlinks.json so verification passes and the URL bar stays hidden.
step
for the localhost PWA, skip TWA and ship a minimal WebView APK.
artifact
one full-screen Activity loads the loopback origin; cleartext to localhost is opted in because it is off by default before API 37 (the localhost case).

<!-- AndroidManifest.xml: opt into cleartext to the loopback server -->
<application android:usesCleartextTraffic="true">
  <activity android:name=".MainActivity" android:exported="true">
    <intent-filter>
      <action android:name="android.intent.action.MAIN" />
      <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
  </activity>
</application>
apply
the Activity loads http://localhost:8080 in a full-screen WebView; no Digital Asset Links run, so no URL bar appears.
command
build and install like any app: ./gradlew assembleRelease, then adb install app-release.apk.

the bundle: source for the localhost WebView app

scope
this chapter is the runnable source behind the localhost path (the localhost case, the worked example) — a full-screen WebView on http://localhost:9682/memories/, tangled to a buildable tree.
note
no TWA, no Digital Asset Links — the app is a plain WebView, so the URL bar never appears and no verification runs.
tangle
three blocks land under /var/run/user/1000/memories-webview/ — the manifest, the Activity, and the build script — with package com.example.memorieswebview.
command
once tangled, run it inside the flake’s devShell — nix develop /home/sam/prog/devel/flakes/android# --command bash build.sh — which compiles, dexes, signs and emits build/memories-webview.apk; then adb install build/memories-webview.apk places it. (No adb reverse here — the server is on the device’s own loopback per the target’s setup.)

<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.example.memorieswebview">
  <application
      android:label="Memories"
      android:usesCleartextTraffic="true">
    <activity
        android:name=".MainActivity"
        android:exported="true"
        android:theme="@android:style/Theme.NoTitleBar.Fullscreen">
      <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
      </intent-filter>
    </activity>
  </application>
</manifest>


package com.example.memorieswebview;

import android.app.Activity;
import android.os.Bundle;
import android.webkit.WebView;
import android.webkit.WebViewClient;

public class MainActivity extends Activity {
    private WebView webView;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        webView = new WebView(this);
        webView.getSettings().setJavaScriptEnabled(true);
        webView.setWebViewClient(new WebViewClient());
        webView.loadUrl("http://localhost:9682/memories/");
        setContentView(webView);
    }

    @Override
    public void onBackPressed() {
        if (webView.canGoBack()) {
            webView.goBack();
        } else {
            super.onBackPressed();
        }
    }
}


#!/usr/bin/env bash
set -euo pipefail

HERE="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
cd "$HERE"

SDK="${ANDROID_SDK_ROOT:?set ANDROID_SDK_ROOT (the flake devShell provides it)}"
BT_DIR=$(ls -1 "$SDK/build-tools" | sort -V | tail -1)
BT="$SDK/build-tools/$BT_DIR"
PLATFORM="$SDK/platforms/android-34/android.jar"
JAVAC="$(command -v javac || true)"
KEYTOOL="$(command -v keytool || true)"
if [ -z "$JAVAC" ] || [ -z "$KEYTOOL" ]; then
  echo "javac/keytool not on PATH — run inside: nix shell nixpkgs#openjdk" >&2
  exit 1
fi
PKG=com/example/memorieswebview
OUT=build
mkdir -p "$OUT"

"$BT/aapt2" link -I "$PLATFORM" \
  --manifest AndroidManifest.xml -o "$OUT/app-unsigned.apk"

"$JAVAC" -cp "$PLATFORM" -d "$OUT" "src/$PKG/MainActivity.java"
DEXDIR="$OUT/dex"
mkdir -p "$DEXDIR"
"$BT/d8" --output "$DEXDIR" --lib "$PLATFORM" "$OUT/$PKG"/*.class

(cd "$OUT" && zip -q app-unsigned.apk "dex/classes.dex")

KEY="$OUT/debug.keystore"
if [ ! -f "$KEY" ]; then
  "$KEYTOOL" -genkey -v -keystore "$KEY" -alias androiddebugkey \
    -keyalg RSA -keysize 2048 -validity 10000 \
    -storepass android -keypass android \
    -dname "CN=Android Debug,O=Android,C=US"
fi
"$BT/apksigner" sign --ks "$KEY" --ks-key-alias androiddebugkey \
  --ks-pass pass:android --key-pass pass:android \
  --out "$OUT/memories-webview.apk" "$OUT/app-unsigned.apk"

echo "built $OUT/memories-webview.apk"
