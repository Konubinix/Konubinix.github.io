Braindump

how to write and audit a note

what
a note is a self contained org-mode file digging into one subject — a question to answer, or a topic to explore.
how
the title summarizes that subject, and a heading states it in full when the title cannot.
who
the agent that writes is the writer, the agent that audits is the auditor, and the human is the user.

values that an ia agent must respect

How one reads a note

why
a human reads a note top to bottom, following one thread.
rule
the note treats its subject and nothing else — no detour, no meta-commentary, no secondary justification, no iteration, no mistake, whatever the circumstances.
  • why: a writer drifts by default, and no one cares that the writer worked badly on the way.
rule
fewer words is the default.
  • check: note_hedges lists the hedges and emphasis markers lost between a passage and its rewrite.
rule
one word per meaning — a second name for the same thing reads as a second thing.
  • how: when the user gives a second word for something already named, the writer asks which of the two to keep, rather than adopting the new one.
rule
past 7 siblings or 200 lines, go deeper — headings under a parent heading, bullets into sub-bullets.

Where each piece goes

scope
an argdown map takes a graph — an objection, a premise two conclusions share, reasons that hold only combined — since bullet nesting already covers a tree.
rule
two notes never state the same meaning — the duplicate is refactored out and pointed at.
rule
the writer asks the user what to do with a cut piece.
rule
the writer reads or links another note only if the user agrees.
rule
the note being written is the only one edited.

The form of a bullet

rule
the prose of a note is structured — every body line is a bullet of the form - <intention word> :: <claim>.
  • how: the « intention word » is the single word before ::, naming what the line does; any word may serve.
  • scope: tables and footnote definitions keep their own form.
rule
one meaning per bullet.

What a checker can decide

rule
only three flaws are mechanical — a body line that is not a bullet, a bullet with no ::, an « intention word » that is more than one word.
  • scope: a hyphenated compound is one word — au-delà, peut-être — so the checker joins on the hyphen rather than splitting there.
rule
the rest is not mechanisable, and a silent checker is not conformance.
check
note_bullets reports those three flaws for an open note, and a count for each « intention word » in use.

How the file is typeset

rule
the user sets #+filetags and #+KONIX_ORG_PUBLISH_KIND.
rule
a file is opened with the ensure_file_open MCP tool.
  • why: the edit and the emacs buffer then stay in sync, so run_babel and the tangle_* tools use the work as it stands.
rule
the initial prompt is preserved verbatim at the top of the note, in an org comment or under a :noexport: heading.
  • why: a later disagreement about what the note was for then returns to what was actually asked.
rule
the text under a heading is indented two spaces, as in this note.
rule
every line stays under 120 characters, prose wrapping to fit.
  • scope: a keyword line like #+title: cannot be wrapped and is exempt.
rule
French prose carries the espace insécable where French typography asks for one.
  • how: note_insecables inserts U+00A0 before : ; ? ! » and after «.
rule
the writer strips the insécables before editing a typeset note, and restores them after.
  • why: an insécable displays like an ordinary space and defeats the exact string match, so an Edit spanning one silently fails.
  • how: note_strip_insecables runs, then the whole edit pass, then note_insecables.

The audit loop

rule
the auditor is a different party from the writer, and judges without ever editing.
  • why: you are the worst-positioned reader of your own work.
  • how: spawn_auditor bakes these rules in.
rule
each audit covers one fix — the whole patched passage against every rule, not « does this fix it? ».
  • why: a batch is read at one pace, and the fix that needed a fresh look goes by with the rest.
rule
each audit reports every objective flaw found, in one verdict.
  • why: subjective battles never end.
rule
each audit runs on the model the work needs — not Opus for a straightforward command.
rule
the writer asks the user to confirm a new term before using it.
  • why: writers coin very poor terms.
rule
a contested flaw escalates to an adversarial debate.

how to do verified promise driven development

what
a promise is a claim about what the program does for whoever uses it.
what
a story is the sequence of whats somebody really performs.
what
a test is the file on disk that runs a story.
how
the code holds the promise, and the test measures that it still holds in time.

The promise and its measure

A test asserts a promise

rule
a story names the promises it asserts.
  • why: everything else a test could check is a measure of a promise the program makes.
  • rule: a story with no promise to name is deleted rather than filed.
rule
the promise is written down, and the test only measures it.
  • why: a promise legible only as a test name is unreadable to the one it was made to.
  • why: docs and tests are two sides of the same coin — the writing states the promise, the test holds it to time.
rule
the promise and its test stand or fall together, in both directions.
  • why: a promise held makes its test green, so a red names the promise that broke.
  • why: the other direction must be earned — a green means the promise holds only if breaking the promise would redden the test.

The promise decides what is measured

rule
a test tries the inputs the promise covers, not every input the code accepts.
  • why: an input the interface never presents measures a promise nobody made.
rule
the promise says when the work is done, never the coverage number.

A reasoning links the stories to the promise

rule
what links a promise and its stories is a reasoning, written beside the promise — these stories passing entails this promise held.
  • why: a red then traces back to the promise that broke.
  • why: unwritten, the next reader guesses the link, and a gap looks like a choice.

The runtime unit is the story

rule
the runtime unit is the story, never the feature.
  • why: a use comes in whole stories — triaging a morning’s photos, running the cabinet frame, picking a few shots to send — and those stories are the promises the program makes.
  • why: a test written per feature asserts a promise nobody holds, since nobody opens a program in order to exercise one button.
what
the what is the desired behaviour.
what
the how is the chosen technical approach.
rule
one function per story runs its whats in the order the person performs them, carrying state from step to step.
  • why: a chain of gestures on one open program is what using it looks like, and an isolated one-gesture run is a path no human takes.
rule
every story is one somebody really lives.
  • how: the user tells the stories and the writer never invents one.
  • how: the writer writes the what, the how and the tests, and assembles them into the stories it was told.
  • why: there are very few of them, because a story is a whole real use rather than a feature.
rule
between them the stories reach every promise the program makes — that reach is the semantic coverage.
  • why: a promise no story reaches goes unmeasured.
  • how: the writer finds the gap and must propose it; the user decides.
  • how: a what that fits no story is that signal — either one is missing from the set, or nobody does that thing, and which it is is the user’s call.
rule
ground walked twice is cut.
  • why: it is time spent measuring a promise already measured.
  • how: the writer suggests the stretch to cut and the user cuts it.
  • scope: stories overlap a little whatever happens, each one opening the program and loading the same first screen, and that much is irreducible.
  • scope: the user may bend a story so that it stops short of showing the whole thing, when the reasoning shows the trimmed part is measured elsewhere.
    • why: what is protected is semantic coverage, not the walking of every path.

The cycle

The cycle is the unit of change

rule
the cycle is the unit of change.
  • why: each step exists because the previous one is provably insufficient.
  • why: skipping a step leaves a gap the next regression will fall into.
rule
the baseline run covers the whole suite.
  • why: a subset baseline proves only that subset was green, and says nothing about pre-existing reds elsewhere.
  • why: a red lit by the post-change run then cannot be dated — your change, or already broken before you started.
rule
the baseline run is gated like any other action.
rule
a codebase that is red and not flaky has its tests fixed before the task at hand resumes, unless the user explicitly asks otherwise.
rule
a promise is measured by the suite the cycle runs, and by nothing else.
  • why: a measure taken anywhere else is one no cycle can cite.

Red proves the test

rule
a test that has never been observed failing has not been observed.
rule
a test that passes for the wrong reason is worse than one that fails for the wrong reason.
  • why: a wrong-failure test still points at a real fault to hunt; a wrong-pass test sits green and hides a gap the suite reports covered, and its green is indistinguishable from outside, so it survives every whole-suite run.
rule
the test is written first and watched failing before any production code changes.
  • why: that failure is what establishes that the test measures the promise it names.
  • why: without it, a passing test proves only that the assertion compiles — the path it claims to cover may already be wired, or the assertion silently vacuous.
rule
the failure mode and message are part of the test’s value.
rule
reverting the change makes the test fail again.
  • why: a red observed once is a fixed point, and failing again confirms the test rides on the new code.
  • why: a test that cannot be made to fail by reverting the change measures no promise in particular.
rule
a test that was restructured rather than written earns its red again, by breaking the promise it names and watching it fail.
  • why: a restructuring starts and ends green, so the moment that would have shown the test still bites never arrives (see the wrong-pass rule above).
  • why: the failure names which test catches the break, so one that has drifted to where an earlier test already covers it is visible as well.
  • how: break one behaviour at a time, in the production code, and require the named test to be the one that fails; a break nothing catches is a test that claims a promise it does not read, and a break something else catches first is a promise measured elsewhere.
rule
a promise that cannot be broken from where the suite stands is recorded as such, in writing, with the reason.
  • why: otherwise it is indistinguishable from one nobody has got round to breaking, and the next reader spends the effort again.
  • why: the reason is itself a finding — it usually names a boundary the suite cannot reach past, which is worth knowing before trusting what lies beyond it.

Minimum to green, then earn the next line

rule
new behaviour appears under a failing test, and the next test earns the next line.
  • why: code beyond what the failing test demands is untested by definition.
  • why: the coupling keeps the suite a faithful description of the system, every branch tracing back to a test that was once red.
  • scope: a refactor pass adds structure no single test motivates.
  • rule: an anticipated edge case is written as the next failing test, not as a preemptive guard in the current change.

The whole suite measures the whole contract

what
the contract is every promise the program makes to whoever uses it.
rule
a change is verified only when the whole suite is green.
  • why: the new test going green proves its own promise realised, and says nothing about which of the others the change broke.
  • why: implicit dependencies between modules — shared state, cached values, ordering assumptions — surface only when every test runs.
  • why: the test you left out is the one most likely to catch the regression you did not predict.
  • why: a green-to-green refactor can still flip a subtle ordering, a fixture, or a shared helper.
  • why: what each run guards against is unknown ahead of time, which is what makes it a regression rather than an anticipated case.

Refactor lives under green

rule
structural change runs under a green suite.
rule
behaviour is held fixed by the tests, and structure is the only thing allowed to move.
  • why: mixing behaviour change with structure change loses the bisect signal — a test going red mid-refactor no longer tells you whether it caught a regression or reacted to an in-progress edit.
rule
the tests are refactored with the same discipline.
  • why: tests are code, and they drift.
  • why: the refactor-tests step is the only place in the cycle where test debt can be paid without losing signal, the suite being green on both sides of the edit.
  • why: a suite that takes too long stops being run.
  • why: a suite full of duplicated assertions gives false confidence that semantic coverage is broader than it is.

The surface and the data

The promise is made at the seam the user touches

rule
whoever uses the work decides where the seam is — the end user of an application, the programmer calling a library.
  • why: the promise is made at that interface; below it is the how.
rule
assertions probe the observable surface — visible text, public API, exported artifact, ARIA role — not internals like private stores, test-only hooks or implementation-selector classes.
  • why: an internal is the how, so such a test measures the how, and every refactor reddens it.
  • how: the suite reaches for get_by_role, get_by_label and get_by_placeholder rather than CSS selectors that encode the current DOM.
    • why: writing user-level helpers is paid back the first time a refactor changes the markup without changing the behaviour.

A test seeds the world it reads

rule
a test creates the rows it depends on, asserts only on what it created, and removes them again.
  • why: what decides whether a test is reproducible is who put its data there.
  • why: data the environment happened to hold — a live row, a value from a shared dump, a label that was there last month — is state no one pinned.
  • why: a change made elsewhere, a renamed label or a pruned row, then turns the test red with no edit to the code it guards, and the red points at the wrong place.
  • why: a failure that moves on its own is worse than no test.
  • scope: a shared fixture may stand the environment up — a database, a server, a seeded dump — and the test still adds the value it needs, exercises it, and tears it down.
    • why: the green then rides on the code under test and nothing else.

When it goes wrong

Test, don’t patch

what
a bug is a promise found broken.
rule
every fix earns a test — written first, observed red, then made green by the smallest change that satisfies it.
  • why: without a test that captures the bug, the fix is invisible to the suite — no proof the bug existed, no proof it is gone, no defense against its return.
  • why: a bug fix landed without a test recurs, and leaves no record of why the line was added.
  • scope: this is the cycle applied to regression rather than feature work — the bug report is the what, the failing test its translation, the fix the minimum code that turns it green.

A flake is a diagnosis, not a knob

rule
an intermittent red is measured before any limit is touched.
  • why: widening a timeout until it goes quiet raises the threshold at which the cause shows, trading a signal for a longer wait.
  • why: the expected time usually sits far under the ceiling, so the failure is a transient — a CDN stall, a resource race — to remove or isolate.
rule
a timeout is raised only when the measurement shows the expected time nearing it.
  • rule: the new number is justified in a comment.
rule
flakiness that is not obvious to fix earns meaningful logging.
  • why: it helps investigate the next time the flakiness occurs.
rule
moving on a flaky test is the choice of the user, never yours.

rule

rule

authority

Prose is the primary artifact

rule
a literate program is first and foremost a piece of writing, in the :: bullet form above.
  • how: the bullets carry the full reasoning — problem, solution, and motivation.
  • how: a code block is the technical translation of a bullet’s claim.
rule
a code block sits a glance away from the bullet it translates.
  • how: the reader sees the motivating bullet and the whole block without scrolling.
  • how: long code is split with noweb to show only the fragment relevant to the bullet at hand.
rule
the why lives in the bullet that motivates the block, never in a code comment.
  • why: the why is never translated, so no code block can hold it.
  • why: a comment carrying a why — a system state, a design constraint, a justification of structure — is prose stranded in the wrong file, invisible to the prose reader and out of context for the code reader.
  • scope: what remains in code is at most a one-liner annotating the line below.
check
remove all code blocks mentally, and the remaining text still forms coherent and complete prose.
  • why: this is what makes the note literate — code and prose interleaved, not inserted side by side.
  • how: a gap means either a bullet is missing or an existing bullet was paraphrasing a block rather than advancing the reasoning, and the heading is rewritten accordingly.
  • how: the auditor reads the prose-only version and judges whether the prose fulfills the stated need.
    • why: prose coherence has no binary signal, so that reading catches what a passing suite cannot.

Code blocks are not repeated in the export

rule
a code block appears in the export only when the prose talks about it.
  • why: re-showing a block the reader has already seen adds nothing, even when the next block depends on it.
  • why: the dependency is resolved at tangle time, invisibly to the reader.
  • scope: repetition is justified when seeing the surrounding code genuinely helps the reading.

The reader’s flow is sacred

rule
the reader glances at a code block to see how a bullet is concretely coded.
  • how: what breaks the flow — a technical derivation, a self-contained construction whose result the reasoning will consume — moves to its own note, linked from the reasoning where its result is used.
  • rule: a block is taken in at a glance — past 30 lines, it splits.
    • why: past that the reader loses the thread between the sentence that motivated the block and the code that is supposed to translate it.
    • how: the block splits along the seams the prose already has, each responsibility that was introduced as a distinct idea becoming its own block with a sentence of motivation just before, and noweb reassembles the pieces at tangle time.
    • how: a block that resists splitting means the prose has collapsed several ideas into one, so the prose is expanded first and the block splits naturally.
  • rule: a short conversational line stays when it names something the reader is already feeling.
    • why: a line like “let’s see what this gives”, just before a block that produces something visible, paces the flow rather than interrupting it.
    • how: a line that introduces new content instead is a bullet in disguise, and is expanded or cut.
rule
an ungrounded name breaks the flow wherever it appears — prose, comments, docstrings, function names, variable names, symbols, any identifier in any form.
  • why: the reading flow does not care which fence a name sits behind.
  • how: where a forward-reference to a code-level term — a field, a function, a class — hides a readback, removing the term fixes both at once.
    • why: the prose was reaching for the implementation when it should have been naming the need.
  • rule: a reference in the exported flow is grounded in the exported flow.
    • why: content kept out of what the reader will read does not exist for that reader, so grounding that lives only there leaves the reference ungrounded forever.
    • how: either the grounding moves into the export, or the reference leaves it.
rule
prose carries the reasoning a picture cannot state — the motivation, the texture, the judgment.
rule
prose stops re-describing what a picture states better.
  • why: a picture delivers in one glance what a paragraph hands over clause by clause for the reader to reassemble.
rule
the note is a story, not a recitation.
  • why: a note that is technically clear but emotionally flat loses readers as surely as one that breaks flow with detours.
rule
external definitions and references link out, and headings link to each other inside the note.
  • scope: exported content links only to exported content.
  • rule: a note whose outline has grown too long to hold in the head carries a table of contents.
    • why: the whole structure is then visible at a glance and every heading is one click away.
    • how: in org-mode, a #+TOC: headlines N directive placed where the overview belongs, or #+OPTIONS: toc:t to let the exporter render one.
    • scope: a short note with two or three headings does without it.

Prose states the what, the how, and the why

The why

rule
the why is traced back to a constraint, a measurement, or a decision someone actually made.
  • why: a gap in the why is an honest signal that something still needs establishing, and a fabricated why hides that signal and ships a lie in its place.
  • how: the ask goes to whoever can settle the reason.
  • authority: the why behind a choice is always a real one.
rule
a sentence whose only job is to make a paragraph sound complete is removed, not polished.

What earns a block

rule
a block exists only where the prose has made it necessary.
  • why: a block the prose did not lead to means a piece of reasoning is missing.
  • how: the why, the reason for the choice, stays in prose.
  • how: the what is translated into a test.
  • how: the how is translated into code.
  • rule: prose states the problem or need, never a readback of the code.
    • rule: a what is never stated without its why.
    • why: prose that paraphrases the block is duplication, not justification, and a note listing “this does X, that does Y” hands over facts no one asked for.
    • how: the note moves in a single register — I need to meet this objective, so I will do this, and so I will do it this way — need, then intent, then technique.
    • scope: where the gap between intent and form is wide enough that a short readback bridges it, the readback earns its place as a translation aside.
  • scope: this binds the reading, not the source — tangle scaffolding lives invisibly, usually under a :noexport: heading or marked :exports none, and needs no motivating prose because it is not read.
rule
the reading flow is the only criterion.
  • rule: it decides how prose and code are sliced against each other.
    • scope: one block per symbol, several symbols per block, several blocks per symbol are all legitimate.
    • how: the slicing has failed when the reader pauses on a function and asks “wait, what is this for? I was reading about something abstract and I don’t see the connection.”
    • how: boilerplate — every getter and setter of a Java bean, say — does not earn a sentence each.
      • why: that would drown the reader in motivation no one needed.
    • how: a block dropping several unrelated functions under a single vague paragraph calls either for more sentences or for splitting the block, whichever restores the flow.
      • why: it leaves the reader unmoored.
  • rule: it decides where vocabulary lives — the states a field can take, the thresholds that govern behavior and the constants that pace the system are named in prose, not in a type comment listing valid values, a magic number setting a tempo, or a literal fixing a bound.

Where blocks sit

rule
the test, the what, comes before the code, the how.
  • why: that is how we talk to each other — the desired behavior first, then the technique used to achieve it.
  • how: the prose states what is needed and what we are going to do — “we need the list to reject a duplicate,” “so we block creation” — and the block just below is that need made visible, code that happens to be a test.
    • why: the word test barely surfaces in the reading, and the reader meets a promised behavior and, right under it, the code that pins it down.
  • how: a test standing apart as a separate paragraph, not flowing from an explicit assertion in the prose, means a sentence is missing from the narrative.
  • scope: test-specific machinery — a tricky fixture, an unusual harness step — earns a sentence only when it is genuinely hard to follow, which is rare.
rule
a block is laid out against the prose that promises it.
  • rule: each prose paragraph promises one what, and the test block below it checks that promise.
    • why: a test block checking several whats under a single paragraph breaks the prose flow, and the reader cannot trace which sentence promised what the test is checking.
  • rule: a paragraph promising a what sits above the block that actually pins it.
    • why: when a block is only a step — it cannot fail unless an earlier one fails with it — the promise it appears to pin is pinned upstream, so prose that named it here has sent the reader to the wrong paragraph.

[Step, not measure]: a block that cannot fail without an earlier block failing with it is a step, not a measure.
  +> [Pinned upstream]: the promise such a block appears to pin is pinned upstream.
    +> [Prose attributes it upstream]: the prose names the block that actually pins the promise, not the step.
  +> <Drop the step>: a step measures nothing, so it comes out of the story.
    <- [State it leaves behind]: the story may need the state it leaves behind.

[No verdict distinguishes them]: no verdict tells you whether a block is a step or a measure.
  + [One outcome for all]: a story reports one outcome for all its blocks, so pure setup and pure measurement are the same colour from outside.
  +> <Undecidable>: no verdict distinguishes them, so which is which cannot be known.
    <- [Read it off the text]: which blocks earn their slot as steps is read off the text, by asking of each what would die if only this one were wrong.
    <- <Instrument the silent block>: a block that never turns out to be the one that failed is the signature to look for.

<Instrument the silent block>
  <- [A candidate, not an answer]: the signature hands you a candidate, not an answer.
rule
each what stays a visible block in the feature heading that motivated it, tagged with the story it serves via noweb (:noweb-ref triage-body).
rule
the stories come first, in a heading of their own.
  • why: the reader meets what the program is for before meeting its parts, and a block that is only a limb of a story cannot be read until the story binding it has been.

What a test may reach

rule
the code carries nothing that exists solely for the test.
  • why: a data-testid, a hidden hook, a selector or attribute that exists only so a test can reach an element is a path no human will ever take, and the final user never reads a test id.
  • how: when the program turns out hard to test at the seam the user touches, the difficulty is real information, and the fix belongs in the design.
    • why: usually the interface is just as unclear to the user.

Translation asides

rule
where the intent is clear but its shape in code is surprising, a short paragraph acts as a translator’s note — “we want X, but in code this is written as Y because Z”.
  • scope: this explains the gap between intent and form, not what the code does.
  • how: such asides should be rare.
  • how: an aside is clearly identifiable as such, introduced by something like “In practice,” or “Under the hood,”.
  • how: an aside that grows beyond its role, explaining more than the translation gap, moves to its own note the prose points at with a short link.
    • why: it would otherwise break the reader’s flow.
rule
needing an aside is read as a diagnostic before it is written.
  • why: sometimes it reflects a genuine gap between what human language and code can express, which is what the aside is for.
  • why: it can also reveal that the code is poorly organized, the surprising shape that needs a translator’s note simply being the wrong shape.
  • how: where the shape is wrong the code is refactored rather than papered over with an aside.
    • why: the structure of the code is not bound to the structure of the prose — noweb reassembles the pieces at tangle time, so the code can be carved along its own joints.

Rewrite, don’t patch

rule
when something forces the note to change — a bug, an oversight, a change of mind, a breaking change in an upstream library, a refactor that obsoletes an earlier choice — the affected prose is rewritten so it reads as if the issue never existed.
  • why: adding a test and an explanatory paragraph describing the mitigation leaves a visible scar rather than restoring the prose.
  • why: a scar interrupts the reader’s flow just as surely as a detour does.
  • how: the result is not prose that fixes something but prose that was always correct, betraying no trace of the path that led to it.
rule
a scar is retrospective — a trace of a revision already applied, a debate already settled.
  • how: the distinguishing test is tense — a sentence describing a fix already made is a scar and is rewritten, one naming an open question the reader should know about is a caveat and is kept.
  • scope: prospective language is not a scar — honest framing of a value still to validate empirically, of an explicit test plan, or of a guard-rail against a tempting wrong path.
Scar — rewrite:
  "initially at 120 mm/s, since revised to 60 mm/s for volumetric flow"

Caveat — keep:
  "clearance at 0.5 mm — to adjust by trial if the real fit is too loose"

  • how: an empty body, a one-armed conditional, a vestigial helper is each a fragment whose work now lives elsewhere.
  • why: the artifact then reads as if neither prose nor code remembered the revision.
