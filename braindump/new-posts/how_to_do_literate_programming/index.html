How to Do Literate Programming

Braindump

Prose is the primary artifact

rule
a literate program is first and foremost a piece of writing, written in the :: bullet form of the form of body text.
  • how: the bullets carry the full reasoning — problem, solution, and motivation.
  • how: a code block is an inline translation of a bullet’s claim, rendering the technical form of what the bullet already stated.
rule
a code block sits a glance away from the bullet it translates.
  • why: readers’ attention is narrow.
  • ideal: the reader sees the motivating bullet and the whole associated block without scrolling.
  • how: long code is split with noweb to show only the fragment relevant to the bullet at hand.
rule
the why lives in the paragraph that motivates the block, never in a code comment.
  • why: the why is never translated, so no code block can hold it.
  • why: a comment carrying a why — a system state, a design constraint, a justification of structure — is prose stranded in the wrong file, invisible to the narrative reader and out of context for the code reader.
  • scope: what remains in code is at most a one-liner annotating the line below.
check
remove all code blocks mentally, and the remaining text still forms a coherent and complete narrative.
  • why: this is what makes the document literate — code and prose interleaved, not inserted side by side.
  • how: a gap means either a paragraph is missing or an existing paragraph was paraphrasing a block rather than advancing the reasoning, and the section is rewritten accordingly.
  • how: a neutral agent reads the prose-only version and judges whether the narrative fulfills the stated need.
    • why: tests give a binary signal and prose coherence does not, so that reading is a stronger signal than code-level tests alone.

The reader’s flow is sacred

rule
the reader glides through the bullets uninterrupted, glancing at a code block to see how a bullet is concretely coded.
  • how: everything else — detours, meta-commentary, secondary justifications — is removed.
  • how: something valuable that breaks the flow — a technical derivation, a self-contained construction whose result the narrative will consume — moves to an annex, linked from the main narrative where its result is used.
  • rule: the shorter the sentence, the better it serves flow.
    • why: the longer a sentence, the more its message dilutes, and a convoluted clause already costs a glance back.
  • rule: a block is taken in at a glance, around thirty lines at most.
    • why: past that the reader loses the thread between the sentence that motivated the block and the code that is supposed to translate it.
    • how: the block splits along the seams the prose already has, each responsibility that was introduced as a distinct idea becoming its own block with a sentence of motivation just before, and noweb reassembles the pieces at tangle time.
    • how: a block that resists splitting means the prose has collapsed several ideas into one, so the prose is expanded first and the block splits naturally.
  • rule: a short conversational line stays when it names something the reader is already feeling.
    • why: a line like “let’s see what this gives”, just before a block that produces something visible, synchronizes the prose with the reader’s impatience to leave abstraction and see a concrete result, pacing the flow rather than interrupting it.
    • how: a line that introduces new content instead is a paragraph in disguise, and is expanded or cut.
rule
an ungrounded name breaks the flow wherever it appears.
  • why: the reading flow does not care which fence a name sits behind.
  • scope: this holds everywhere the reader’s eyes go — prose, comments, docstrings, function names, variable names, symbols, any identifier in any form.
  • rule: a new term enters the document where the document has just laid out what motivates it.
    • why: referring to a concept the reader has not yet met forces them to suspend reading, which breaks flow as surely as a detour.
    • how: reordering fixes it — the grounding sentence first, then the term that names what was just established.
    • how: when the structure constrains the sequence, the reference itself is deferred — name a more general concept the reader already has, and let the specific term arrive when its time comes.
    • how: where a forward-reference to a code-level term — a field, a function, a class — hides a readback, removing the term fixes both at once.
      • why: the prose was reaching for the implementation when it should have been naming the need.
  • rule: a reference in the exported flow is grounded in the exported flow.
    • why: content kept out of what the reader will read does not exist for that reader, so grounding that lives only there leaves the reference ungrounded forever.
    • how: either the grounding moves into the export, or the reference leaves it.
rule
prose carries the reasoning a picture cannot state — the motivation, the texture, the judgment.
rule
prose stops re-describing what a picture states better.
  • why: a picture delivers in one glance what a paragraph hands over clause by clause for the reader to reassemble.
rule
flow is more than the absence of friction.
  • rule: the reader feels the writer’s thrill, pulled forward by the chain of reasoning and eager to find out how it resolves.
    • why: a document that is technically clear but emotionally flat loses readers as surely as one that breaks flow with detours.
  • rule: a document is a story, not a recitation.
    • why: stakes, a tension building toward a result and a payoff at the end are what carry rigorous content through.
    • why: substance without narrative rarely lands, and style is what makes the logic count.
rule
a concept described elsewhere is one click away.
  • how: external definitions and references link out, and sections link to each other inside the note.
  • scope: exported content links only to exported content.
  • rule: a document whose outline has grown too long to hold in the head carries a table of contents.
    • why: the whole structure is then visible at a glance and every section is one click away.
    • how: in org-mode, a #+TOC: headlines N directive placed where the overview belongs, or #+OPTIONS: toc:t to let the exporter render one.
    • scope: a short note with two or three sections does without it.

Code blocks are not repeated in the export

rule
a code block appears in the export only when the prose talks about it.
  • why: this follows from the reader’s flow — re-showing a block the reader has already seen, because the next block depends on it, adds nothing to the reading.
  • why: the dependency is resolved at tangle time, invisibly to the reader.
  • scope: repetition is justified when seeing the surrounding code genuinely helps the reading.

Prose states the what, the how, and the why

The why

rule
the why is always a real one, traced back to a constraint, a measurement, or a decision someone actually made.
  • why: it is the one thing prose alone carries, and the easiest to fake — a plausible-sounding justification reads almost exactly like a real one.
  • why: a gap in the why is an honest signal that something still needs establishing, and a fabricated why hides that signal and ships a lie in its place.
  • how: a reason that is not known is said to be unknown, asked about, or discussed with whoever can settle it.
rule
a sentence whose only job is to make a paragraph sound complete is removed, not polished.

What earns a block

rule
a block exists only where the prose has made it necessary.
  • why: a block the prose did not lead to means a piece of reasoning is missing.
  • how: the why, the reason for the choice, stays in prose, untranslated.
  • how: the what, the desired behavior, is translated into a test.
  • how: the how, the chosen technical approach, is translated into code.
  • rule: prose states the problem or need, never a readback of the code.
    • rule: a what is never stated without its why.
    • why: prose that paraphrases the block is duplication, not justification, and a document listing “this does X, that does Y” hands over facts no one asked for.
    • how: the document moves in a single register — I need to meet this objective, so I will do this, and so I will do it this way — need, then intent, then technique.
    • scope: where the gap between intent and form is wide enough that a short readback bridges it, the readback earns its place as a translation aside.
  • scope: this binds the reading, not the source — tangle scaffolding lives invisibly, usually in :noexport: sections or marked :exports none, and needs no motivating prose because it is not read.
rule
the reading flow is the only criterion.
  • rule: it decides how prose and code are sliced against each other.
    • scope: one block per symbol, several symbols per block, several blocks per symbol are all legitimate.
    • how: the slicing has failed when the reader pauses on a function and asks “wait, what is this for? I was reading about something abstract and I don’t see the connection.”
    • how: boilerplate — every getter and setter of a Java bean, say — does not earn a sentence each.
      • why: that would drown the reader in motivation no one needed.
    • how: a block dropping several unrelated functions under a single vague paragraph calls either for more sentences or for splitting the block, whichever restores the flow.
      • why: it leaves the reader unmoored.
  • rule: it decides where vocabulary lives — the states a field can take, the thresholds that govern behavior and the constants that pace the system are named in prose, not in a type comment listing valid values, a magic number setting a tempo, or a literal fixing a bound.

Where blocks sit

rule
the test, the what, comes before the code, the how.
  • why: that is how we talk to each other — the desired behavior first, then the technique used to achieve it.
  • how: the prose states what is needed and what we are going to do — “we need the list to reject a duplicate,” “so we block creation” — and the block just below is that need made visible, code that happens to be a test.
    • why: the word test barely surfaces in the reading, and the reader meets a promised behavior and, right under it, the code that pins it down.
  • how: a test standing apart as a separate paragraph, not flowing from an explicit assertion in the prose, means a sentence is missing from the narrative.
  • scope: test-specific machinery — a tricky fixture, an unusual harness step — earns a sentence only when it is genuinely hard to follow, which is rare.
rule
a block is laid out against the prose that promises it.
  • rule: each prose paragraph promises one what, and the test block below it checks that promise.
    • why: a test block checking several whats under a single paragraph breaks the prose flow, and the reader cannot trace which sentence promised what the test is checking.
  • rule: a paragraph promising a what sits above the block that actually pins it.
    • why: when a block is only a step — it cannot fail unless an earlier one fails with it — the promise it appears to pin is pinned upstream, so prose that named it here has sent the reader to the wrong paragraph.
  • rule: each what stays a visible block in the feature chapter that motivated it, tagged with the session it serves via noweb (:noweb-ref triage-body).
rule
the sessions come first, in a chapter of their own.
  • why: the reader meets what the program is for before meeting its parts, and a block that is only a limb of a session cannot be read until the session binding it has been.
── chapter "Use cases", first in the note ────────────────────────
Prose: "the triager starts from the unsorted pile, narrows to what
        per is sorting, then works photo by photo — retagging,
        redating, filing"

  [wrapper — :noweb-ref tests
     @testcase
     def test_triage_a_morning(page):
         <<triage-body>>]

── feature chapter "Searching and filtering" ─────────────────────
Prose: "a label narrows the grid to the photos carrying it"

  [block — :noweb-ref triage-body
     type the label, commit, assert only those photos remain]

── feature chapter "The lightbox" ────────────────────────────────
Prose: "a wrong date is fixed on the photo itself"

  [block — :noweb-ref triage-body
     open the photo, edit its date, assert the grid re-orders]

Prose: "a duplicate in the list would make the tally incoherent,
        so we block creation and display an error message"

  [test — translates "we block and display a message"]
  [code — translates "we validate the list and expose a createError getter"]

What a test may reach

rule
every test exercises the program the way the final user does — same surfaces, same gestures, same outputs.
  • why: the closer the test’s path matches the user’s, the more its green bar means the promised behavior actually holds.
  • rule: the code carries nothing that exists solely for the test.
    • why: a data-testid, a hidden hook, a selector or attribute that exists only so a test can reach an element is a path no human will ever take, and the final user never reads a test id.
    • how: the test reaches for the handles the user has — the visible label, the role, the rendered text.
    • how: when the program turns out hard to test that way the difficulty is real information, and the fix belongs in the design.
      • why: usually the interface is just as unclear to the user.

Translation asides

rule
where the intent is clear but its shape in code is surprising, a short paragraph acts as a translator’s note — “we want X, but in code this is written as Y because Z”.
  • scope: this explains the gap between intent and form, not what the code does.
  • how: such asides should be rare.
  • how: an aside is clearly identifiable as such, introduced by something like “In practice,” or “Under the hood,”.
  • how: an aside that grows beyond its role, explaining more than the translation gap, moves to an annex the prose points at with a short link.
    • why: it would otherwise break the reader’s flow.
rule
needing an aside is read as a diagnostic before it is written.
  • why: sometimes it reflects a genuine gap between what human language and code can express, which is what the aside is for.
  • why: it can also reveal that the code is poorly organized, the surprising shape that needs a translator’s note simply being the wrong shape.
  • how: where the shape is wrong the code is refactored rather than papered over with an aside.
    • why: the structure of the code is not bound to the structure of the prose — noweb reassembles the pieces at tangle time, so the code can be carved along its own joints.
Prose: "we want the getters to behave as real properties"

  Under the hood, this means using defineProperty rather than Object.assign,
  which does not copy accessors.

  [code — translates this technical constraint]

Rewrite, don’t patch

rule
when something forces the document to change — a bug, an oversight, a change of mind, a breaking change in an upstream library, a refactor that obsoletes an earlier choice — the affected prose section is rewritten so it reads as if the issue never existed.
  • why: adding a test and an explanatory paragraph describing the mitigation leaves a visible scar rather than restoring the narrative.
  • why: a scar interrupts the reader’s flow just as surely as a detour does.
  • how: the result is not a narrative that fixes something but one that was always correct, betraying no trace of the path that led to it.
rule
a scar is retrospective — a trace of a revision already applied, a debate already settled.
  • how: the distinguishing test is tense — a sentence describing a fix already made is a scar and is rewritten, one naming an open question the reader should know about is a caveat and is kept.
  • scope: prospective language is not a scar — honest framing of a value still to validate empirically, of an explicit test plan, or of a guard-rail against a tempting wrong path.
Scar — rewrite:
  "initially at 120 mm/s, since revised to 60 mm/s for volumetric flow"

Caveat — keep:
  "clearance at 0.5 mm — to adjust by trial if the real fit is too loose"
rule
when reasoning leaves the code — a justification moved to prose, a constraint absorbed into a cleaner design — the code that only carried it leaves as well.
  • how: an empty body, a one-armed conditional, a vestigial helper is each a fragment whose work now lives elsewhere.
  • why: the artifact then reads as if neither prose nor code remembered the revision.
